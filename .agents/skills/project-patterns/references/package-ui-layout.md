# Package UI Layout and Clay Shell

- Before reviewing or changing package UI, SDUI, shell layout, styling, or input routing, load `clay-ui` and the mandatory `impeccable`, `full-output-enforcement`, `high-end-visual-design`, `design-taste-frontend` skills. Every UI task in a plan lists these skills in `Documentation Reviewed`; no subset selection.

Decision source: `decision-logs/2026-06-09-1431-clay-owned-shell-layout-and-package-ui-contribution-model.md`.

- Clay owns the package-facing application shell, working area, pane/split tree, fixed pane slots, component registry, style/theme token model, and action routing contract.
- Packages declare inert, validated UI/layout/input/action/data/style contributions; they must not mutate host layout, inject uncontrolled host CSS, call raw `Deno.core.ops`, or receive direct Tauri APIs.
- Target renderer is a Clay-owned React component registry in the Tauri webview. Stable package node IDs become React reconciliation keys. Current Masonry widgets remain migration inventory only and are removed after parity.
- First-party trusted UI modules may be compiled into the frontend. Third-party UI remains declarative by default; arbitrary custom UI runs only in an isolated webview/iframe with a typed message boundary and no direct Tauri IPC.
- Long-term UI structure is: working area -> pane/split tree -> pane/window layout -> mandatory `main` container plus optional `left`, `right`, `top`, and `bottom` slots -> Clay React components.
- Empty/new-tab `main` is a generic pane-content contribution (one winner), not a product-named pane kind. Default first-party landing is `@clay/chat`. `WelcomeWidget` is core fallback when none is loaded (Open File / Open Folder only). Tab bar, Command Centre, and native dialogs stay host-owned. Decision: `decision-logs/2026-08-21-2152-product-surfaces-are-replaceable-packages.md`.
- Panels can be fixed (participate in layout) or transient (overlay/dismissible); packages may request defaults, but Clay validates composition and users may override through documented configuration APIs.
- Styling uses centralized Clay theme tokens, typed component style variables, semantic package tokens, CSS custom properties generated by the host, and CodeMirror theme adapters. Packages cannot inject uncontrolled global CSS or renderer callbacks into host UI.
- Plans that modify packages, modes, SDUI, layout, styling, input routing, or package configuration must keep `docs/reference/packages/creating-packages.md` current with implemented APIs, examples, limitations, tests, and migration notes.
- Phase 20 multi-document sessions, dirty/save status chrome, and recovery menus are Clay-owned shell surfaces. Packages may bind documented command IDs and contribute inert UI around them; they must not own tabs, native save dialogs, clipboard-contents APIs, or reconnect/resync loops. See the Phase 20 authoring contract section in `creating-packages.md`.
- Product landings and agent chrome are package SDUI (`product-surfaces-are-packages.md`). Plan 087 “packages cannot replace welcome” applies only to the core fallback, not the loaded entry surface.
- Markdown and future modes must consume these generic shell/layout primitives rather than adding mode-specific Rust layout branches or fixture-only side panels.

## Transient Menu Surfaces (Command Centre)

Decision source: `decision-logs/2026-08-11-1711-command-centre-surface-path-mode-and-sequence-keybindings.md`.

- One shared `TransientMenuSession`-based surface hosts command-palette, path-browsing, and picker sessions; add new session kinds, not new overlay systems.
- Menu sessions are server-owned and interactive via protocol round-trip (query/selection/activate/cancel intents, server-pushed snapshots); the client only renders and forwards keystrokes while a modal session is active.
- New overlay anchors extend the `TransientMenuOrigin` enum (e.g. centred Spotlight-style); backdrop effects use theme tokens (scrim), never custom render-pipeline work beyond Masonry/Vello upstream.
- Filtering is a shared Clay-owned fuzzy subsequence matcher used by all transient menus, not per-menu ad-hoc filters.
