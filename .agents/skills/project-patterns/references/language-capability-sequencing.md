# Language Capability Sequencing

- After Phase 18, generic editor capabilities must land before Phase 19 hot reload: transient menu/command execution, generic text/code fallback modes, package-provided syntax grammars, completion, workspace/file navigation, Git package foundations, then first-party language package expansion.
- Syntax highlighting runs through a tiered tree-sitter engine behind one generic grammar→category pipeline (decision `2026-07-09-0352`, supersedes the earlier web-tree-sitter-only choice). Tier 1 = native compiled-in `tree-sitter-*` crates for first-party Rust/TypeScript/JavaScript/Markdown (bundled grammar *data*, dispatched by grammar/extension through one generic engine — **no per-language Rust branches**). Tier 2 = host-side `web-tree-sitter` WebAssembly adapter for third-party/override languages. Tier 3 = per-package JS parser fallback for languages with no grammar. Adding a first-party language is a Clay rebuild; adding a third-party language is a package with no rebuild.
- `@clay/rust`, `@clay/typescript`, and `@clay/javascript` begin as grammar-only first-party packages: grammar/query assets, syntax metadata, style-token mapping, and provenance. They do not become full modes until later phases expand them through generic primitives.
- Active major mode and active syntax grammar are related but separate. Grammar packages may attach syntax to `core.code`/`core.text` fallback documents without declaring a full language mode.
- Clay core owns generic grammar contribution contracts, validation, parse scheduling, decoration transport, and hot-path safety. Language packages own grammar/query assets and package-visible metadata.
- Arbitrary third-party grammar/native artifact loading stays out of scope until a dedicated security/trust decision defines integrity, sandboxing, and user authorization.
- The syntax vocabulary is the theming contract: LSP `SemanticTokenType` + `SemanticTokenModifiers` as the base set, extended with a small Clay-owned prose set (heading-1..6, strong, emphasis, code-span, code-block, list-marker, link, quote). A `DecorationSpan` carries two orthogonal axes — `token_type` and text-attribute `modifiers` (bold/italic/underline/strikethrough/...) — not a free-form `style_token`. An open-string escape with prefix fallback lets third-party packages mint new tokens a theme can still catch.
- Theme registry is the single source of color: a `StyleRegistry` maps `token_type + modifiers → StyleSpec{color,bold,italic,underline,strike}` plus base UI colors. Hardcoded `Color` constants in `src/editor/surface.rs` are deleted; paint reads from the active theme. Theme packages publish inert style overrides; one active theme via `setTheme()` in `init.js`. Shipped: Gruvbox Material Dark + Light.
- Decorations are layered additive merge (Syntax/Semantic/Diagnostic/Search), not single-owner override. "Override native" = user-initiated engine selection (Tier 1 vs Tier 2/3), never silent package self-promotion.
- Open-time parse must be non-blocking (document text renders first, `DecorationSet` paints asynchronously), and handler errors must surface as `RuntimeDiagnostic`s instead of being silently dropped by `ParseCoordinator::finish_task`. Markdown decorations fold onto the generic pipeline; the Markdown preview SDUI panel stays package-JS.
- LSP language intelligence is an opt-in package, never core: a `@clay/lsp-*` package bridges LSP responses to Clay primitives and may start only a fixed manifest contribution under an explicit deny-by-default `language-server` grant bound to package provenance, canonical executable/literal argv, approved inherited-environment names, and known directory roots. Bundled package trust/load never auto-grants it; revocation/reload/root removal/runtime replacement terminates sessions. This is trusted same-user subprocess authority—not OS filesystem/network/process confinement—per decision `2026-07-14-2023`.
- Language package plans must include primitive review, package-provided grammar resolution tests, disabled/invalid package fallback tests, docs/registry/wiki coverage, and no language-specific Rust branches.
