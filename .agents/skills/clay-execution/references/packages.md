# Packages, Modes, and Authority

## Package Runtime Trust Domains

Sources: `decision-logs/2026-07-21-0001-two-package-runtime-trust-domains.md` (partially supersedes `2026-06-27-2014-unified-user-authorized-package-authority.md`).

- Exactly two persistent JS package-runtime trust domains: trusted Clay/bundled code (integrity-verified bundled packages) and one shared adopted-third-party runtime. Never promote third-party to trusted through normal approval.
- Classify trusted packages by compiled bundled inventory plus exact provenance/integrity, never package name/prefix or normal user promotion.
- Install distinct `deno_core` op extensions, module-loader allowlists, state, heap/time budgets, and generation lifecycles. Third-party runtime installs only documented public package ops and narrow host state; Clay-internal ops are absent, not hidden by facades.
- Cross domains only through typed, bounded, inert Rust-mediated values. Never share V8 objects, functions, globals, module instances, promises, or raw internal ops.
- Third-party packages form one disclosed shared trust cohort (not isolated from each other); host APIs still stamp provenance and enforce grants, graph edges, generations, and revocation.
- Third-party mutation of first-party behavior requires a target-declared extension point plus exact user approval; extension/replacement never becomes impersonation. Approved replacement withdraws the first-party package while replacement code stays in the third-party runtime with its own provenance. Clay core/bootstrap is not package-replaceable.
- Plans changing package runtime, package APIs, first-party packages, or composition must include domain-boundary, extension-point, adoption/revocation, cross-domain deny, and third-party shared-cohort tests.

## Package Distribution

Sources: `decision-logs/2026-05-08-1958-clay-js-api-naming-and-package-distribution.md`, `decision-logs/2026-06-27-2014-unified-user-authorized-package-authority.md` (user-controlled package graph retained; same-runtime/source-ceiling rules superseded), `2026-08-30-2153-st-package-name-arnilo-scope-and-npm-distribution.md` (`@arnilo/st`, npm + GitHub releases, pi install model; `clay install` appends `loadPackage` in `init.js`; Homebrew deferred).

- Expose package management through both a `clay package ...` CLI and an in-app package UI, backed by one shared package-management service/path.
- Do not implement a package manager or registry: delegate fetching, dependency resolution, version ranges, lockfiles, integrity, caching, and registry access to an existing npm-compatible JavaScript package manager (pnpm/npm-compatible preferred).
- Clay owns the package contract: manifest validation, package identity/prefix, capabilities/permissions, runtime vs load-time entry separation, behavior manifest contributions, mode declarations, package graph relations, conflict metadata, enable/disable/remove state, user authorization state, documentation/registry integration.
- Installation is separate from execution: install downloads/records via the package manager; enable/load validates Clay metadata, permissions, docs, compatibility; runtime JS executes server-side through Clay's JS runtime; clients receive validated behavior manifests/SDUI/protocol updates, never arbitrary package JavaScript.
- Package APIs must use the package name or registered prefix for exported Clay JS APIs (`vimEnableMode`) so provenance is visible.
- Each JS package is explicitly loaded from `~/.clay/init.js`; packages never become behavior-changing defaults silently.
- Preferred end-user setup is a one-line explicit load (`loadPackage("@clay/markdown")` or equivalent); ordinary defaults work without copied manifests or primitive-by-primitive boilerplate. If a package cannot support one-line loading because Clay lacks a generic primitive, plans identify the primitive gap and document longer setup as a temporary fallback.
- Package metadata eventually includes: package prefix, runtime entry, load-time/behavior entry when present, permissions, modes, docs, Clay JS API dependencies.
- Valid package sources: npm registry, GitHub/git URL, tarball, local path — routed through the shared package manager/source resolver. npm-compatible remains the default implementation boundary.
- Packages may request capabilities to depend on, import/use, extend, disable, or replace other packages. Cross-domain mutation requires a target-declared public extension point plus explicit user approval; Clay must show, record, enforce, and revoke every grant.
- Plans that add package behavior must include documentation-as-code coverage for package APIs, commands, key bindings, configuration options, permissions, modes, and behavior manifest contributions.

```bash
clay package add @clay/vim; clay package remove @clay/vim; clay package update; clay package list
```

## Binary Provisioning

Source: `decision-logs/2026-09-08-2141-binary-provisioning-deny-by-default-table.md`.

- Feature-referenced external binaries live in one data table (`src/packages/binaries.rs`); adding a binary is a one-line table change, never per-binary code branches.
- Presence checks are user-triggered only (`clay install` with no spec); they reuse each feature's fail-closed resolution (explicit configured path → PATH → documented absolute fallback) and never run at startup or in hot paths.
- Install requires explicit per-invocation approval: `clay install --bin <name> --yes`. Without `--yes`, Clay prints the exact command and changes nothing; there is no interactive prompt and no silent install.
- Lifecycle scripts stay off unless `--allow-scripts` is passed on the same invocation; the approval is per-invocation and recorded in output.
- Installs route through the shared npm-compatible manager backend into the Clay-owned package store (`<store>/node_modules/.bin`); provisioning never touches package records, grants, or the install ledger, and features keep their own fail-closed resolution (provisioning places files only).
- Entries without a verified npm binary package are presence-only: Clay prints the manual command and never spawns. Removal is a documented per-entry command, not binary-specific code.

## Package Manifest Single Source

Source: `decision-logs/2026-08-18-1758-single-manifest-package-loading.md`.

- `clay.contributions` in `package.json` is the **only** package registration data path. Load entries (`load.js`) execute code only (import parse modules, wire bridge factories). No imperative registration calls in first-party package load ceremony.
- Imperative registration APIs (`serverRegisterModePattern`, etc.) are reserved for user `init.js` configuration and runtime contributions.
- Tier 1 native grammars: the Rust `NativeGrammarDescriptor` owns grammar data, queries, and style maps. First-party package.json files do **not** declare `syntaxGrammars` — a package-side `styleMap` for a native grammar is dead data that will drift.
- Manifests may declare a `preset` (`code-mode`, `prose-mode`, `lsp-bridge`) that expands into the standard permissions, `apiDependencies`, extension points, and contribution families for the archetype; validation runs on the expanded set; explicit deviating declarations win over preset defaults. Source: `2026-08-18-1758-package-capability-presets.md`.
- A new code-language package should be a manifest with `preset: "code-mode"` plus only deviating declarations and a load entry that imports code — not copied boilerplate.

## Authority Boundaries

Source: `decision-logs/2026-07-17-1841-phase20-daily-editing-semantics.md` (daily editing), `2026-07-01-0350-phase18-9-generic-text-code-fallback-modes-and-key-behavior.md` (core modes), `2026-07-14-2023-language-server-package-authority.md` (external processes), `2026-08-03-1859-editor-control-trust-boundary-for-editor-ops.md` (editor-control), `2026-08-11-1711-command-centre-surface-path-mode-and-sequence-keybindings.md` (browse grant), `2026-08-13-2223-degraded-language-server-grant-tolerated-at-load-package.md` (grant degradation), `2026-08-23-0052-tauri-react-client-architecture.md` (client migration).

**Core rule: server-authoritative documents with optimistic client shadows.**

- Server owns: canonical document ropes/state; versions and transaction ordering; edit validation/correction; file/workspace authority and environment-specific operations; open document registry; editable leases and read-only observer state; region/document/behavior/workspace locks; JS extension execution and behavior definitions; AI/tool orchestration and mutation authority.
- Client owns: Tauri-hosted React rendering, DOM accessibility, input presentation; CodeMirror `EditorState`/`EditorView` hot-path editing state; viewport/caret/selection/pointer/focus and local UI transient state; local document shadow/cache; pending edit queue and client transaction IDs; execution of server-issued hot-path behavior manifests through bounded frontend adapters.
- Tauri Rust owns only window/webview lifecycle, narrow OS integration, server process/connection management, and frontend-DTO↔server-protocol translation. It never becomes canonical document/package/workspace authority.
- Document access: one editable lease per document; other clients are read-only observers; lease transfer/release explicit. Protocol/plan language must preserve the final model.
- Daily editing (Phase 20): undo/redo is per-document client history of inverse insert/delete/replace ops applied as ordinary optimistic `Edit`s under the lease (server undo-unaware); clipboard is client OS-mediated through `ClipboardSink` with explicit user commands (no server clipboard proxy); IME preedit is client paint-only until `Commit` becomes one ordinary edit (cancel on focus loss, document switch, before undo/redo); multi-document keeps the server as open-registry/lease/dirty authority while the client holds a bounded session map keyed by server `DocumentId`. Package/configuration/AI authority over clipboard/filesystem/shell/network/raw ops is NOT finalized by Phase 20 semantics — ships Clay-owned user commands only on existing selected-file/workspace-root paths.
- Built-in `core.*` modes: always-on `core.text` (universal) and `core.code` (code-like extensions / any shebang), registered at startup via `register_builtin_mode` (no `init.js`, no `loadPackage`), granting no package authority. `core.`/`clay.` mode-ID prefixes are reserved; `register_mode`/`register_minor_mode` must reject them. Built-in manifests ship without an owning package (`select_behavior_manifest_for_document` bypasses package-record lookup on the `core.` prefix). Classification probing reads only a bounded constant prefix (`MAX_LEADING_CONTENT_BYTES = 512`) of an already-open document — never a filesystem scan or package-supplied predicate. Mode-discovery commands (`modes.listActiveModes`/`explainActiveMode`) are read-only `ServerFirst` built-ins with empty permissions via `CommandExecutor::execute_discovery`; no execution/document/workspace authority.
- External process authority: package-triggered external processes require a dedicated deny-by-default capability and an approved decision log; never silently compose from package load, first-party trust, `shell`, or `filesystem`. Bind approval to package provenance, a fixed inert contribution, canonical executable, literal argv, explicit inherited-environment names, known workspace roots. Runtime input selects only an already-approved contribution/root. Launch without a shell, clear environment by default, bound I/O/time/concurrency, terminate on revocation/reload/root removal/runtime replacement/shutdown. This is trusted same-user subprocess authority — the working directory/root-bound grants constrain Clay's API/audit identity, not the OS; call it trusted subprocess authority, never sandboxed. Keep process work out of typing, paint, layout, scroll, and local text-application paths.
- Editor control (`editor-control`): access to client-local editor state (caret/selection) requires BOTH an approved permission AND an exact-mode declaration (`clay.editorControl.modes`); enforce per call, deny-by-default; never grant "editor access" wholesale. Gate in the shared op path (`require_current_package_capability` provenance + active-major-mode membership) — same gate for first- and third-party; trusted callers without a package context (user configuration) are the only gate-free path. The third-party worker holds no mode registry/document scope — replicate the active mode snapshot across the worker bridge (push on state change + rewire). Server→client programmatic triggers use an advisory bounded push (`EditorCommandRequest` boxed wire variant); the client re-parses command IDs deny-by-default through the keybinding dispatch path and drops unknown/non-editor IDs. Conflicts between packages in one mode: coexist, no arbitration — the user deactivates packages; revocation takes effect on runtime-generation replacement.
- Built-in browse grant: user-driven navigation inside a Clay-owned built-in surface (e.g. Command Centre path mode) implicitly authorizes filesystem traversal outside granted workspace roots; packages never receive equivalent authority. Converting a browsed path into durable access still requires an explicit grant (`SingleFile` on open, `Directory` root grant via the tab/workspace binding path). Browse listings stay bounded (depth 1, entry caps) and are never read on paint/layout paths.
- Language-server grant degradation: `loadPackage` tolerates a missing/stale/revoked `language-server` grant — the capability stays inert because session start and every analyzer invocation re-check a current exact grant covering the workspace root. All other capability grants keep their hard load-time requirement. Analyzer registration (`language.serverRegisterDocumentAnalyzer`) needs the package enabled and a fixed package language server contribution, but not a current grant; a generation reload skips analyzers without a current grant instead of failing. Bundled defaults never auto-grant language-server authority; a replacement package never inherits the replaced target's grant.
- Planning guidance: do not describe the server as a stateless behavior service; do not make the client canonical "for convenience"; a simplified in-memory server document is a minimal server-canonical placeholder; prefer per-document owner/actor boundaries over global locks; no runtime config knob for built-in fallback mode or transform toggles (declaring a package mode is the override path; `setPackageOption`'s closed suffix allowlist rejects `core.preferredFallbackMode`/`electricCharacters`/`pairInsertion`/`commentContinuation`).

## Long-Lived Package Document Analysis (LSP workers)

Source: `decision-logs/2026-07-15-1750-lsp-document-sync-and-package-worker-authority.md`.

- One bounded worker per package/contribution/root/runtime generation. Bind each worker to exact package provenance, contribution grant, canonical workspace root, and runtime generation; use resolver-recorded package modules, never callback values or arbitrary module URLs.
- Full canonical open/reset text and accepted unsaved deltas require BOTH `parse-document` and the exact `language-server` grant. Expose only server-stamped identity/version, canonical root path, validated root-relative path, UTF-8 text, and accepted byte-range deltas — never client intent, rope/filesystem handles, environment values, or unrelated documents.
- Local edit acknowledgment and paint stay wait-free; analysis state submits only after canonical acceptance through bounded non-blocking mailboxes; pressure coalesces to one latest reset.
- Core owns generic event ordering, worker/session lifecycle, limits, provenance, cancellation, stale rejection, validated publication, cleanup. Package code owns protocol framing/state, capability negotiation, synchronization mapping, positions, URIs, server policy.
- Ceilings: 4 workers, 32 documents / 8 MiB text per worker, 256 KiB per document, 1 MiB serialized frames. Above ceilings: never partial child state — clear package outputs, one sanitized status, retain mode, Tier 1 syntax, base completion, commands, previews.
- Disable/revoke/remove/update/root removal/last close/runtime replacement/failure/shutdown cancels work, clears cached outputs, terminates worker and child within bounded graceful/kill deadlines. No automatic restart loops. Worker confinement is NOT an OS sandbox; retain trusted-subprocess disclosure.

## Extensions and AI

Sources: `decision-logs/2026-07-16-1825-phase19-hot-reload-transaction-and-stale-edit-semantics.md`, `2026-08-11-0352-configuration-watch-auto-reload-and-modular-structure.md`.

- Package/mode logic runs server-side through `deno_core`, not in Tauri Rust or React hot paths. Extensions register commands, modes, UI declarations, permissions, behavior definitions; the server compiles registrations into behavior manifests and SDUI updates rendered by the Clay-owned React registry.
- First-party trusted presentation modules may be compiled into the frontend; third-party custom UI requires an isolated surface and cannot receive direct Tauri IPC.
- Ordinary typing never synchronously waits on package JS execution or React rerenders.
- Hot reload: prepare/validate a fresh runtime-generation candidate while the current generation stays active; no live-state mutation during evaluation. Serialize reload attempts; acquire `LockScope::Behavior` only for the final compare-and-swap commit; typing/background parsing never wait on JS evaluation. Commit all generation-owned server contributions once, then broadcast one bounded complete snapshot per affected connection; clients validate and atomically install before acknowledging. Commit is the rollback boundary: pre-commit failure preserves the old generation; post-commit failure recovers from latest state and never restores revoked authority. Revoke old executable authority logically at commit; terminate old workers/sessions afterward under bounded cleanup. Use built-in `runtime.reloadConfiguration` through normal command execution; it ships with default `Ctrl+Shift+R` and a config-root watcher triggers the same serialized reload service (no reload-specific IPC).
- AI mutation: reads/proposals may be unlocked; edits carry document version, behavior version, range, permission scope; lock only the required scope (range/document/behavior/workspace); behavior-changing sessions lock behavior/document scope until the new manifest installs; clients never grant AI direct local mutation authority.
- WASM is future architecture unless explicitly in scope; if introduced require stable ABI, capability/permission model, fuel/time limits, memory limits, deterministic host APIs, versioned manifests, registry entries.

## Agent Host

Sources: `decision-logs/2026-08-21-1758-native-prism-host-no-acp-cli-parity.md` (host/no ACP; partially superseded for React-facing AG-UI), `2026-08-21-2152-product-surfaces-are-replaceable-packages.md` (package-owned profiles/landings), `2026-08-23-0052-tauri-react-client-architecture.md` (AG-UI at the frontend transport boundary), `2026-08-30-2159-obscura-web-browser-stack-and-computer-use-linux.md`, `2026-08-30-2157-default-acceptance-workspace-free-host-write-gated.md`, `2026-08-30-2200-pi-tree-model-extended-to-workspace-checkpoints-and-discard.md`, `2026-08-30-2201-workspace-scoped-session-search-shared-by-clay-and-st.md`, `2026-09-07-2149-prism-0.5.1-clay-agent-family-pins.md` (0.5.1 pins), `2026-09-16-0026-prism-0.7.0-clay-agent-family-pins.md` (live pins 0.7.0; Node ≥ 22; unknown agent events drop), `2026-09-02-1440-direct-external-coding-agent-adapters.md`, `2026-09-14-1705-workspace-scoped-agent-sessions.md` (session ownership and tool-authority root).

- First-party agents run in a Clay-owned Node ≥ 22 child (`clay-agent`) via Prism `createAgent`/`createAgentSession`/`AgentEvent`. Never inside `deno_core`. ACP stays out of the first-party path.
- `clay-agent` keeps its Clay-owned internal protocol to the Rust server; the server adapts bounded events into AG-UI for the React-facing stream over Tauri channels. AG-UI is not a daemon replacement and adds no localhost listener.
- Server owns session identity, transcript, selected profile/provider/model, mutation. React paints and forwards composer input. Typing/paint never wait on the daemon.
- Package JS cannot spawn or speak to the daemon — core spawns, not a package-triggered process grant.
- Credentials: Clay vault + Prism credential resolvers. No `process.env`, no secrets in events/logs/menus/a11y.
- Agent profiles are `AgentDefinition`s registered by packages, not compiled core stubs. `@clay/coding-agent` (Phase 29) registers Coding Agent; later Work/PA/Research are more packages on the same kernel, store, and `agent.*` APIs.
- Coding-agent CLI parity uses Prism tool factories plus Clay `ReadOperations`/`WriteOperations`/`EditOperations` over the document registry — never `createAcpFilesystemOperations` or ACP `fs/*`.
- Host-owned binaries (Obscura engine, graft CLI, `computer-use-linux` MCP, `agy`) follow one pattern: fail-closed resolution, daemon-managed lifecycle, capabilities hidden when absent, never package-spawned.
- Agent *types* are configuration, not code: one directory per type under `~/.clay/agents/`, enumerated by a directory scan (no package load) and named on the wire only as a bare contained name (never a path). A tab's agent is tab chrome (`TabCommand::SetAgent`, validated server-side); the switch re-reads only that agent's own config (system prompt, skill roots, tool caps, MCP servers, model/effort defaults) over the same session, and one agent's grants are never widened by another's (per-session MCP allow-lists, per-root tool caps). Plan 118 task 35.
- MCP config-sourced stdio servers (decision 2026-09-09-1341) are the one exception to approval-gated process authority: user-owned `~/.clay/agents/<agentId>/mcp.json` (per-agent layout, decision 2026-09-09-1420) and repo-root `.mcp.json` connect without an approval gate, and bare command names may PATH-resolve there (Claude Code parity; user owns server choice). Package JS still never supplies argv; literal argv + explicit env names + server/tool caps stay fail-closed. Any new process-granting surface needs its own decision log — this exception does not compose.
- Acceptance policy: workspace = full agent freedom; host reads free; host writes outside workspace gated on explicit permission; opt-in full-autonomy toggle (clay and `st` alike).
- Session trees are pi-model JSONL trees (`id`/`parentId`, `/tree`, branch summaries, `/fork`/`/clone`) linked to document version checkpoints at task boundaries; `st` iterations checkpoint git + documents + session entry together so any branch is discardable post hoc (three layers, one action).
- One SQLite session/branch/checkpoint store serves clay + `st`, keyed by stable workspace identity. Clay-owned FTS searches current-workspace user/agent messages, branch summaries, plan/task metadata, and OM reflections; raw tool output stays out by default. Search results resume/open exact tree entries but never become agent context without explicit user action; `st` contributes workflow labels, never a second store.
- Pin `@arnilo/prism*` and AG-UI packages to exact reviewed versions. Live pins: Prism 0.7.0 — the seven adopted families (`@arnilo/prism`, `@arnilo/prism-core`, `@arnilo/prism-providers`, `@arnilo/prism-coding-tools`, `@arnilo/prism-web-tools`, `@arnilo/prism-memory`, `@arnilo/prism-mcp`) at exact `0.7.0` plus direct `better-sqlite3@13.0.3` and `playwright-core@1.63.0`; import explicit subpaths only (`@arnilo/prism-core/credentials/node`, `@arnilo/prism-core/sessions/sqlite`, `@arnilo/prism-providers/<adapter>`); never retired 0.3 package names or the 27 exports removed in 0.5.
- Provider-mandatory wire requirements (e.g. OpenCode Go's `x-opencode-session`) are Prism-side knowledge enforced deterministically since 0.5.1 (kernel fills `options.sessionId`/`cacheKey`, default cache breakpoints, `ProviderRequirementError` fail-fast). Hosts never hand-wire per-provider request policies — do not register `createSessionCachePolicy` or session-policy overlays on `createAgent`. Per-prompt effort goes through `RunOptions.thinkingLevel` on `session.stream`. MCP goes through `@arnilo/prism-mcp` public API only — never import SDK v2 modules in clay-agent.
- The Rust event mapper (`src/server/agent/run.rs` `map_event`) maps named Prism `AgentEvent` types only; an unknown `type` returns `None` (dropped, not forwarded). Never resurrect the catch-all that synthesized `AgentWireEvent::Started` — it left runs "streaming" forever (`agent_suspended` incident) and would reopen on Prism 0.7 `attention_compiled` / `subagent_*` / `delegation_*`. A lifecycle type Clay must render gets an explicit arm (map subagent lifecycle onto existing `Tool` events, do not invent wire variants speculatively).
- External coding agents are direct core-owned runtimes, never Prism providers or package-spawned processes. Their adapters expose a small lifecycle/event bridge plus declared capabilities; vendor loop/session context stays with the vendor while Clay owns the delegation record, policy projection, lifecycle, redaction, and UI truthfulness. Translate Clay tools through MCP separately from agent control. Claude Code uses its Agent SDK with isolated settings, explicit tools/MCP, approval mediation; Antigravity headless uses configured policy and must advertise no live Clay approval until a documented control protocol exists. PTY is fallback for native vendor controls, not a semantic adapter.
- Agent session ownership is the workspace, not the process: one `(workspace root, agent type)` → one daemon session, and a tab *looks up* that session rather than owning one; two tabs on one folder share its session (decision 2026-09-14-1705).
- Every agent tool call resolves its workspace from the **session** (session id → recorded workspace root → registered root id) and fails closed when that root does not resolve. Never bind agent tool authority to a launch cwd, a bootstrap workspace, a first-configured root, or the active tab — those are the fallbacks that let a tool read or write a folder the session does not own (MCP allow-lists come from the session's own root too).
- Frontend agent session state is per tab (one `AgentSessionModule` + transport per tab, disposed with the tab), never a module/process singleton, and the relay is routed by session id (`threadId`/`state.sessionId`); a tab's own tab-stamped STATE answer is the authority for which session it owns.
- Provider/model/agent/setup pickers are Command Centre session kinds, not extra dropdown widgets; entry-surface buttons invoke the same commands.

## Product Surfaces Are Packages

Source: `decision-logs/2026-08-21-2152-product-surfaces-are-replaceable-packages.md`.

- Default landing, Chat, Coding Agent, and later Work/PA/Research are first-party JS packages on Clay primitives — not compiled irreplaceable chrome. Canonical enablement is one `loadPackage` line.
- Third-party packages may `replaces` those packages or `extends` declared extension points with exact user approval; replacement stays in the third-party runtime. Core/bootstrap and `clay-agent` are not packages.
- Empty/new-tab `main` hosts at most one pane-content contribution; none → core fallback (Open File / Open Folder only). No product-named pane kinds (`Agent`) for replaceable surfaces.
- Clay core owns pane topology, React component registry, Command Centre, tab bar, Tauri OS dialogs, Prism daemon, vault, `agent.*` authority. Packages declare inert SDUI and call documented APIs; they never spawn the daemon or receive direct Tauri IPC.
- Plans that add a product landing or agent ship it as a bundled first-party package with extension points, one-line load, unload→fallback tests, replace/rollback tests. No core disabled stubs for future agents.

## Mode Primitive-First Planning

Sources: `decision-logs/2026-06-04-1923-replace-markdown-parser-with-markdown-it-and-primitive-first-mode-planning.md`, `2026-06-26-1338-phase18-7-persistent-runtime-and-js-parsehandler-bridge.md`, `2026-07-01-0350-phase18-9-generic-text-code-fallback-modes-and-key-behavior.md`.

- Every plan implementing a new editor mode or JS mode package includes a dedicated primitive-review task before package implementation. It reads primitive reference docs and implementation wiki first: `docs/reference/primitives/index.md`, `docs/reference/primitives/registry.md`, `docs/wiki/modules/primitive-architecture.md`, `docs/wiki/modules/rendering-primitives.md`, `docs/wiki/modules/parse-coordinator.md`, `docs/wiki/modules/decoration-transport.md`, and mode/package-specific wiki pages.
- Plan package behavior in this order: inventory existing generic Rust primitives → document what can already be achieved → identify gaps → add only generic reusable primitives when needed → implement the JS package on top.
- Rust server/client code must not add mode-specific branches for package behavior; new primitives must be reusable by future modes.
- Generic open-time mode activation is implemented through the persistent server-side JS runtime plus token-backed JS→Rust `ParseHandler` bridge; future modes reuse `loadPackage`/`clay:modes`/`clay:parse`/`ParseCoordinator` — no new mode-specific Rust open-time branches or parser calls.
- Persistent runtime parser authority is constrained: only resolver-validated first-party packages register live handlers; Rust stores tokens, not JS function values; executable callback fields stay rejected; parse work is background/bounded; no filesystem/network/shell/AI/WASM/raw-op/native-widget/client-JS/package-manager authority is added.
- Primitive changes include documentation/test work so every primitive is recorded in reference docs, wiki pages, master wiki index, and deterministic coverage tests (`tests/primitives_docs.rs` or successor).
- AI agents working on a JS package consult the primitive wiki before designing package code.
- Built-in fallback modes: `core.text`/`core.code` registered at startup via `register_builtin_mode` (no `init.js`, no `loadPackage`). Classification precedence ladder: user override > package-declared pattern (exact filename > wildcard > extension > MIME) > shebang > bounded leading-content probe (512 bytes, open-path-supplied) > `core.code` > `core.text`. Equal-precedence ties: package beats built-in; same-provenance ties raise `AmbiguousClassification`. `core.*`/`clay.*` mode IDs reserved; language packages extend built-ins through the same generic primitives.

## Language Capability Sequencing

Sources: `decision-logs/2026-06-29-2006-package-provided-grammar-and-capability-phases.md`, `2026-07-08-2316-web-tree-sitter-host-adapter-for-syntax-highlighting-and-non-blocking-open-parse.md` (superseded on engine choice), `2026-07-09-0352-tiered-tree-sitter-themable-syntax-vocabulary-theme-registry-and-opt-in-lsp.md`, `2026-07-14-2023-language-server-package-authority.md`, `2026-08-18-1758-decoration-background-axis.md`, `2026-08-18-1758-document-typography-size-ladder.md`.

- Capability order after Phase 18: transient menu/command execution, generic text/code fallback modes, package-provided syntax grammars, completion, workspace/file navigation, Git package foundations, then first-party language package expansion — all before Phase 19 hot reload.
- Syntax highlighting: tiered tree-sitter engine behind one generic grammar→category pipeline. Tier 1 = native compiled-in `tree-sitter-*` crates for first-party Rust/TypeScript/JavaScript/Markdown (bundled grammar *data*, dispatched through one generic engine — **no per-language Rust branches**). Tier 2 = host-side `web-tree-sitter` WebAssembly adapter for third-party/override languages. Tier 3 = per-package JS parser fallback when no grammar exists. First-party language = Clay rebuild; third-party = package, no rebuild.
- `@clay/rust`, `@clay/typescript`, `@clay/javascript` begin as grammar-only first-party packages (grammar/query assets, syntax metadata, style-token mapping, provenance); they become full modes only later through generic primitives. Active major mode and active syntax grammar are separate; grammar packages may attach syntax to `core.code`/`core.text` documents without declaring a full mode.
- Arbitrary third-party grammar/native artifact loading stays out of scope until a dedicated security/trust decision defines integrity, sandboxing, and user authorization.
- Syntax vocabulary is the theming contract: LSP `SemanticTokenType` + `SemanticTokenModifiers` base set, extended with a small Clay-owned prose set (heading-1..6, strong, emphasis, code-span, code-block, list-marker, link, quote). A `DecorationSpan` carries two orthogonal axes — `token_type` and text-attribute `modifiers` (bold/italic/underline/strikethrough/...) — never a free-form `style_token`. An open-string escape with prefix fallback lets third-party packages mint new tokens a theme can still catch.
- Theme registry is the single color source: `StyleRegistry` maps `token_type + modifiers → StyleSpec` with an opaque **foreground** color plus optional **background** axis and a bounded, theme-owned **size-scale ladder** keyed by `TokenType`. Foreground colors are opaque (no tint-alpha washes); paint reads backgrounds before text and applies per-token scale in layout rebuild.
- Decorations are layered additive merge (Syntax/Semantic/Diagnostic/Search), not single-owner override. "Override native" is user-initiated engine selection (Tier 1 vs Tier 2/3), never silent package self-promotion.
- Open-time parse is non-blocking (text renders first, `DecorationSet` paints asynchronously); handler errors surface as `RuntimeDiagnostic`s, never silently dropped by `ParseCoordinator::finish_task`. Markdown decorations fold onto the generic pipeline; the Markdown preview SDUI panel stays package-JS.
- LSP language intelligence is an opt-in package, never core: a `@clay/lsp-*` package bridges LSP responses to Clay primitives, may start only a fixed manifest contribution under an explicit deny-by-default `language-server` grant bound to package provenance, canonical executable/literal argv, approved inherited-environment names, known directory roots. Bundled trust/load never auto-grants; revocation/reload/root removal/runtime replacement terminates sessions. Trusted same-user subprocess authority — not OS confinement.
- Language package plans include: primitive review, package-provided grammar resolution tests, disabled/invalid package fallback tests, docs/registry/wiki coverage, no language-specific Rust branches.

## Package UI and Shell Layout

Source: `decision-logs/2026-06-09-1431-clay-owned-shell-layout-and-package-ui-contribution-model.md`, `2026-08-11-1711-command-centre-surface-path-mode-and-sequence-keybindings.md`, `2026-08-21-2152-product-surfaces-are-replaceable-packages.md`.

- Clay owns the package-facing application shell, working area, pane/split tree, fixed pane slots, component registry, style/theme token model, action routing contract. Packages declare inert, validated UI/layout/input/action/data/style contributions; they must not mutate host layout, inject uncontrolled host CSS, call raw `Deno.core.ops`, or receive direct Tauri APIs.
- Renderer is the Clay-owned React component registry in the Tauri webview; stable package node IDs become React reconciliation keys. The native Masonry client was deleted at migration completion (Plan 097 Phase 12); do not reintroduce a second production client. TauRPC remains optional bridge glue, accepted only after an exact-version compatibility spike; it does not replace Clay's server protocol.
- First-party trusted UI modules may be compiled into the frontend; third-party UI stays declarative by default; arbitrary custom UI runs only in an isolated webview/iframe with a typed message boundary and no direct Tauri IPC.
- Long-term UI structure: working area → pane/split tree → pane/window layout → mandatory `main` container plus optional `left`/`right`/`top`/`bottom` slots → Clay React components.
- Empty/new-tab `main` is a generic pane-content contribution (one winner), not a product-named pane kind. The first-party landing is the launcher surface (its own plan 118 task); `WelcomeWidget` is the core fallback when no landing package is loaded (Open File / Open Folder only). Tab bar, Command Centre, native dialogs stay host-owned. Plan 087 "packages cannot replace welcome" applies only to the core fallback, not the loaded entry surface.
- Panels are fixed (participate in layout) or transient (overlay/dismissible); packages may request defaults, but Clay validates composition and users override through documented configuration APIs.
- Styling: centralized Clay theme tokens, typed component style variables, semantic package tokens, CSS custom properties generated by the host, CodeMirror theme adapters. Packages cannot inject uncontrolled global CSS or renderer callbacks into host UI.
- Plans modifying packages, modes, SDUI, layout, styling, input routing, or package configuration must keep `docs/reference/packages/creating-packages.md` current with implemented APIs, examples, limitations, tests, migration notes (see `references/docs-as-code.md`).
- Phase 20 multi-document sessions, dirty/save status chrome, recovery menus are Clay-owned shell surfaces; packages may bind documented command IDs and contribute inert UI around them, never own tabs, native save dialogs, clipboard-contents APIs, or reconnect/resync loops.
- Markdown and future modes consume generic shell/layout primitives — no mode-specific Rust layout branches or fixture-only side panels.
- Transient menu surfaces: one shared `TransientMenuSession`-based surface hosts command-palette, path-browsing, picker sessions; add new session kinds, not new overlay systems. Menu sessions are server-owned and interactive via protocol round-trip (query/selection/activate/cancel intents, server-pushed snapshots); the client only renders and forwards keystrokes while a modal session is active. New overlay anchors extend the `TransientMenuOrigin` enum; backdrop effects use theme tokens (scrim). Filtering is the shared Clay-owned fuzzy subsequence matcher, used by all transient menus.
