# Protocol, Performance, and Behavior Manifests

## IPC Protocol

Sources: `decision-logs/2026-08-25-1253-chunked-document-loading.md`, `2026-07-16-1825-phase19-hot-reload-transaction-and-stale-edit-semantics.md`, `2026-07-17-1841-phase20-daily-editing-semantics.md`, `2026-07-19-0351-low-latency-incremental-syntax-decoration.md` (supersedes `2026-07-19-1912-syntax-decoration-continuity-and-complete-authoritative-replacement.md`), `2026-07-19-2238-exact-range-provisional-decoration-replacement.md`, `2026-08-26-1838-server-syntax-sessions-and-atomic-viewport-patches.md`, `2026-08-26-2137-lezer-fail-fast-before-server-syntax-overhaul.md`, `2026-08-27-0159-resume-server-authoritative-editor-performance.md`, `2026-07-01-0350-phase18-9-generic-text-code-fallback-modes-and-key-behavior.md`.

- Keep protocol semantics separate from codec implementation. Rust server transport stays on `rkyv` behind a small length-prefixed codec boundary; Tauri Rust translates validated server messages into bounded JSON-compatible frontend DTOs and typed channels; React never decodes archived bytes.
- Validate received archived bytes before access; bound frame sizes before allocation; treat ALL IPC input as fallible, even local IPC.
- Carry final-compatible metadata: `document_id`, `client_id`, editable/read-only access state, `lease_id` when editable, base document version, server version, client transaction ID, behavior version.

## Performance Rules

- No full-document IPC for ordinary edits. No synchronous server/JS round trip before rendering normal typing. No Tauri/server IPC wait in CodeMirror transaction application, React render, layout, or browser input handlers.
- Bounded queues for outgoing client edits; per-document edit ordering, never global serialization; deltas/transactions instead of snapshots (except an atomically installed runtime-generation replacement whose mutually dependent state fits one bounded frame).
- Initial tab load, selected/path open (`DocumentOpened`), reload (`DocumentReloaded`), resync, and persisted-document restore use bounded chunked transfer: a head message carrying the first chunk plus total byte length, then versioned client-driven `DocumentChunkRequest`s clamped to `MAX_CHUNK_BYTES`, served by rope slices — never whole-document single-frame text. Runtime-generation refresh uses bounded rope inputs rather than full open-document strings. The per-file open gate is replaced by a server-owned session resident-memory budget plus binary sniffing; neither is user configuration. Editing gates on per-document load completion; typing never waits on chunk fetches. Trusted-runtime public open/reload JSON APIs retain an explicit heap-safe bounded contract.
- Runtime-generation snapshots: existing 1 MiB frame ceiling, complete latest-state recovery after broadcast lag, one client acknowledgement only after validation and atomic install. Consider diffs/chunking only after measured payload/install thresholds justify a separate decision.
- Daily-editing local application (undo/redo inverse apply, clipboard cut/paste, IME preedit paint, active-document chrome switch) stays off IPC waits; save/conflict/open authority remain server-first/background relative to paint. Bound undo history at 256 entries per document and retained client document sessions at 64; clear a document's undo/redo on full resync/hard open-replace.
- Make UI-reactive server work cancellable and priority-aware. Advisory syntax runs through one bounded latest-wins session per document/grammar; connection dispatch returns after canonical work and required responses; native parser work runs on a bounded blocking executor, never directly on Tokio workers.
- Viewport syntax uses explicit request IDs and complete success/empty/rejected atomic patches. Tauri may coalesce obsolete whole patches only; it must never coalesce required sibling patch members independently.
- Keep package-selected syntax authority and executable syntax-management behavior server-side. CodeMirror owns local text/viewport and inert render projection, not arbitrary package parser execution. A client-local parser is a separate metric-gated decision, not the default fix.
- Fail fast before any client-local parser spike: check current-language grammar freshness, real WebKitGTK edit/long-task latency, distant 10–50 MiB viewport freshness, the 256 MiB envelope, and same-document four-pane scaling, in that order; stop on the first hard failure. Reopen frontend-worker parsing only if the completed server-session path still misses approved metrics and traces attribute the delay to server/bridge placement.
- Incremental syntax highlights parse once per accepted document version/grammar stream over a stable bounded window, using exact edit metadata and changed-range queries; decoration transport/cache chunking must not multiply parser jobs over the same window. Newer syntax versions cancel or coalesce superseded work, but the latest edit stays eligible immediately; no whitespace-only or idle-only parse scheduling.
- Client decoration state may interpolate inert spans through optimistic edits; server-issued current-version syntax remains authoritative. Narrow-token inheritance: existing narrow syntax may inherit appended Unicode alphanumeric/underscore suffixes; whitespace, newline, punctuation, structural edits end it.
- Every authoritative decoration chunk contains complete capture state for exactly the UTF-8-safe range it replaces; expand changed-range query coverage to complete touched replacement chunks before publication; never publish a wider authoritative range than fully queried.
- Applying current authoritative decorations replaces only the declared viewport: subtract that exact range from overlapping provisional package/layer state, preserve geometry outside it, coalesce only local compatible residuals; never delete a whole provisional chunk merely because it overlaps authority.
- Syntax sits beneath slower semantic layers; stale decoration versions are rejected; no client parser unless measured optimized server latency justifies a separate decision.
- Keep background AI/indexing/file work from delaying input confirmations or UI-reactive work.
- Internal editor performance traces are schema-versioned, disabled by default, bounded per process, source-free; reuse existing transaction IDs for profiled edits, carry optional numeric IDs on viewport/parse/decorations; report p50/p95/max only from local developer snapshots.

## Behavior Manifests

Core rule: the server owns behavior definitions; the client executes only inert, versioned behavior manifests for latency-sensitive hot-path behavior.

- Use a behavior manifest when: a keypress should be client-first and predictable; editor mode behavior must be immediate (Enter indentation, Tab, bracket/quote pairing, list/comment continuation); the client must route keybindings without asking the server synchronously; UI-reactive behavior needs triggers/priorities/cancellation policy.
- Never for: arbitrary JS in the client, file/workspace/shell/network/AI side effects, unknown extension commands, long-running computation, security-sensitive permission decisions.
- Classify commands/key behavior as one of: `ClientFirstPredictable` (apply locally, async transaction), `ClientFirstRequiresAck` (apply locally, expect confirmation/correction), `ServerFirst` (send intent, wait for server result), `ServerFirstWithLock` (server locks range/document/behavior/workspace before mutation), `UiReactivePriority` (async cancellable UI work, e.g. completion/diagnostics), `Background` (never delays edits or UI-reactive work).
- Generic key-behavior kinds (Phase 18.9): `TextTransform` kinds — pair insertion `PairRule`, comment continuation `CommentContinuationRule`, Tab `TabRule`, Enter `EnterRule`, electric characters `ElectricCharacterRule` + `ElectricEffect` — reusable across all modes. Ship two default rule sets: `EditorBehaviorRules::default_text()` / `BehaviorManifest::minimal_text_editing` (no electric) and `EditorBehaviorRules::default_code()` / `BehaviorManifest::core_code_editing` (electric outdent for `}`/`)`/`]`).
- Electric characters are the only new manifest *kind* — an extension of the `EnterRule`/`PairRule` family, not a new primitive *category*. Only Rust-known engines execute them (`insert_electric_with_event`, `dedent_leading_one_level` in `src/editor/surface.rs`); package JSON parsing accepts only the `outdent-one-level` effect and drops unknown effects; future effects each need a Rust-known engine.
- Built-in `core.*` modes ship their own default manifests without an owning package; `select_behavior_manifest_for_document` detects the `core.` prefix and bypasses package-record lookup. Source: `decision-logs/2026-07-01-0350-phase18-9-generic-text-code-fallback-modes-and-key-behavior.md`.
- Versioning: edits carry `behavior_version` + base document version; manifest/runtime-state updates are validated and installed atomically from the client's point of view, acknowledged only after complete installation; hot reload publishes a new runtime generation and manifest version. Retain only the immediately previous inert manifest for already-rendered edits — never its runtime, workers, sessions, grants, providers, or callbacks. Previous-generation `Edit`/`EditorIntent` operations pass validation only before the connection acknowledges the new generation and within the fixed two-second/256-accepted-transaction grace; old commands and provider/output work never receive grace. After grace: reject with `InvalidBehaviorVersion`, republish latest runtime state, canonical document resync. Source: `decision-logs/2026-07-16-1825-phase19-hot-reload-transaction-and-stale-edit-semantics.md`.

## Maintenance Validation

- Prefer automated checks over instruction-only maintenance for docs, wiki indexes, generated registries, public API coverage. Checks fail with actionable repair commands (`cargo run --bin update-doc-registry`), detect stale artifacts in test/CI, and never silently mutate files.
- Planned Clay checks: wiki index links every wiki page; Clay JS API docs are linked from `docs/index.md`; generated documentation registry is current; server-side Rust public functions have Clay JS APIs; Clay JS APIs have Markdown docs plus generated registry entries.
- Wiki pages and code must not contradict each other. When they disagree, match reality; prefer deleting dead code over re-documenting it when there are zero callers.
- Platform-gated code Linux CI never compiles must be either wired to a real caller or deleted; unreachable platform code is rot, not support. Native picker implementations for pending platform targets stay out until the platform phase lands; docs name them as targets, not shipped behavior.
- Deleting a Rust module: clear every metadata citation in the same change — `clay_js_api_inventory` path-existence guards (`source_paths_named_by_public_metadata_exist`, `inventory_rust_paths_name_existing_source_files`) — by updating affected Markdown `backing_rust` fields and `api-inventory.toml`'s `backing_rust`/`current_rust_owner`, then rerun `cargo run --bin update-doc-registry`. Source: `decision-logs/2026-08-31-1745-delete-dead-native-dialog-backends.md`.

## Testing Guidance

Plans involving protocol/performance include tests for: codec round trips; oversized frame rejection; invalid archive rejection; delta edit messages with version metadata; behavior manifest round trips when relevant; non-blocking editor behavior when the IPC consumer is absent or slow.
