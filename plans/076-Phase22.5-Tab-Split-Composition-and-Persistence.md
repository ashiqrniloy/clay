# Phase 22.5: Tab × Split Composition and Persistence

This plan implements `roadmap.md` Phase 22.5. It closes the two remaining
composition gaps of the Phase 22 window model and makes the whole window
state durable: (1) verified, test-guarded composition — every tab owns its
split tree and per-pane state (already structurally true since 22.3: each
`TabChrome` carries its own `WorkingAreaLayout`), with split/close/focus-pane
commands provably operating only within the active tab, and tab
move/reorder provably keeping each tab's internal state intact; and (2)
persistence — tab order, active tab, per-tab workspace root, per-tab split
tree (topology + ratios + slot sizes), and per-pane open documents survive a
full restart and reconnects through an extended `layout.json`.

Architecture: **client-owned persistence, server-rebuilt registry.** The
client already owns `layout.json` (src/shell/layout_persist.rs, Phase 20.3)
and every piece of restored state (split trees live in `TabChrome`,
per-pane document identity in the pane views); the server's `TabRegistry`
stays in-memory and is rebuilt at startup through the exact 22.3 lifecycle
path (`TabCommand::New` per restored tab, `Activate` for the persisted
active tab) — no new protocol messages, no new server ops, no new authority.
Every restored tab goes through the same validation as a user-opened tab:
connection caps, handshake authentication, `WorkspaceState::add_root`
canonicalization, and the existing `OpenDocument` path validation. Restore
is the new-tab flow (`client::connect` → `mount_tab` → `TabCommand::New`)
driven by a persisted description instead of a folder dialog, plus a split
tree rebuild and per-pane document reopens that reuse the 22.3 reconnect
reopen machinery (`documents_for_reopen` precedent, `pending_opens`
per-pane attribution).

Scope boundary: Phase 22.5 ships **composition guards + multi-tab
persistence/restore of layout.json**. It does **not** persist unsaved edits
(full restart drops them, consistent with today's quit semantics; the 22.4
confirm/save flow covers explicit tab close), restore caret/viewport/scroll
state (documents reopen fresh from the server), add a quit-time dirty
confirm (recorded in Further Actions), persist per-tab pane-focus-policy
runtime changes (config-driven via `setPaneFocusPolicy`), add server-side
disk registry or multi-client/multi-window persistence (Phase 21), or add
a11y/perf budgets (22.6).

Confirmed architecture decisions (roadmap Phase 22 preamble + Plans
072/073/074/075): each tab owns its split tree (one workspace per tab);
each tab is a real separate client connection with server-authoritative tab
state; panes are generic workspace-bound content hosts; maximum 4 panes per
tab (`MAX_PANES_PER_TAB`, src/shell/layout.rs:21); tab order/active/binding
is server-authoritative and reorderable (protocol v13, 22.4).

Entry gate: `plans/075-Phase22.4-Keyboard-Tab-Management.md` must have zero
unchecked tasks. Run `npx ui-skills start` before UI design tasks (the 22.5
UI surface is verify-only — persistence changes no chrome).

## Objectives

- Composition is provably correct: split/close/focus-pane commands and pane
  event routing operate only within the active tab (guard tests prove no
  cross-tab mutation), and tab move/reorder keeps every tab's split tree,
  per-pane documents, and active pane intact.
- `layout.json` becomes a versioned multi-tab document: tab order, active
  tab, per-tab workspace root, per-tab split tree topology + ratios + slot
  sizes, per-tab active pane, and per-pane open documents (workspace-root
  relative paths). Legacy single-tab (Phase 20.3) files keep restoring.
  Corrupt/missing file → today's default bootstrap, no panic.
- Full restart restores the whole window: tabs mount in persisted order
  with persisted workspaces, split trees rebuild, documents reopen into
  their panes, and the persisted active tab + per-tab active pane get
  focus. Unrestorable entries (workspace gone, over connection cap, over
  pane cap) are skipped with diagnostics, never fatal.
- Reconnects keep restoring from retained in-memory state exactly as 22.3
  (persistence writes continue through multi-tab sessions — the 22.3
  single-tab-only save guard is lifted).
- Linux blocking validation passes: `cargo fmt --check`, `cargo check
  --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test
  --all-targets`.

## Expected Outcome

- A user with N tabs (each with up to 4 panes, custom split ratios, slot
  sizes, and open documents) quits and relaunches Clay: the same tabs in
  the same order, same workspaces, same split trees, same documents in the
  same panes, same active tab and active panes appear; unsaved edits are
  gone (documented restart semantics).
- Pane commands issued in one tab never mutate another tab's tree; moving
  tabs never disturbs their internals — both guarded by tests.
- Persistence is transparent: single-tab behavior and the legacy
  `layout.json` shape behave exactly as pre-22.5; no new user-facing
  command, key binding, configuration option, package surface, protocol
  message, or authority grant.
