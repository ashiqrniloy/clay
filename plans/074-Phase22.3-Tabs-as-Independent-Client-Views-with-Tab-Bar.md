# Phase 22.3: Tabs as Independent Client Views with Tab Bar

This plan implements `roadmap.md` Phase 22.3. It turns the Phase 22.1/22.2
single-connection window (one `EditorWidget` chrome, one `WorkingAreaLayout`
split tree, per-pane `PaneDocumentView`s, one shared `ClientEditQueue`) into a
multi-tab window where **each tab is a real separate client connection**: opening
a tab calls `client::connect(endpoint)` to establish its own `ClientSession`
(own `ClientEditQueue`, event stream, `ClientInitialState`), its own
`EditorWidget` chrome (SDUI/panel/overlay/runtime-generation owner), its own
`WorkingAreaLayout` split tree, its own workspace roots, open documents, active
modes, and retained sessions — isolated from other tabs. Tabs share the existing
`MAX_ACTIVE_CONNECTIONS = 64` permit pool. A server-authoritative in-memory tab
registry (order, active tab, per-tab workspace + client binding) makes tab
structure survive client reconnects. A tab bar chrome row at the top of the
window (below the top fixed panel slot, above the working area) shows each tab's
workspace name with a close button and switches on click; it is hidden when only
one tab is open so single-tab behavior matches today exactly.

Scope boundary: Phase 22.3 ships **the tab = real-client model, the tab bar, and
the in-memory server-authoritative tab registry surviving client reconnects**.
Phase 22.3 does **not** add tab key bindings or user-rebindable tab command IDs
(22.4 — the tab bar's click/close affordances are the only tab UI in 22.3),
persist the tab registry or per-tab split trees/per-pane documents to disk
(22.5 — `layout.json` extension), or add full accessibility roles/announcements
and CI performance budgets beyond the focused guards listed here (22.6). Tab
reorder/move (drag or keyboard) is 22.4; the registry stores order for
restoration but is not reordered in 22.3 (tabs append in open order). The full
dirty-document confirm/save flow on tab close is 22.4; 22.3 close-tab preserves
data safety by blocking close of a tab with unsaved edits (reusing the existing
dirty detection) and defers the polished save/confirm menu.

Confirmed architecture decisions (roadmap Phase 22 preamble + Plans 072/073):
each tab owns its split tree (one workspace per tab); each tab is a real separate
client connection with server-authoritative tab state; panes are generic
workspace-bound content hosts, never tied to files in the split model; maximum 4
panes per tab; duplicate file opens are blocked within a workspace; every Phase
22 key binding will be user-editable through `init.js` (arrives 22.4). Authority:
server owns canonical documents/versions/leases/workspace/file authority and the
tab registry; client owns rendering, viewport/focus/split-tree transient state,
and per-tab connection lifecycle.

Entry gate: `plans/073-Phase22.2-Pane-Document-Views-Within-One-Workspace.md`
must have zero unchecked tasks. Use the current project UI skill requirements before UI design tasks.

## Objectives

- Each tab is a real separate client: opening a tab establishes its own
  `client::connect` `ClientSession` with independent workspace roots, open
  documents, active modes, and retained sessions, isolated from other tabs and
  sharing the existing `MAX_ACTIVE_CONNECTIONS` connection caps.
- Server-authoritative tab registry: the server holds tab order, the active
  tab, and per-tab workspace + client binding in memory, so tab structure
  survives client reconnects and reconnect restoration, consistent with the
  client-authority model, lease accounting, and connection caps.
- Tab bar chrome at the top of the window (below the top fixed panel slot, above
  the working area), shown whenever more than one tab is open; each tab card
  shows the workspace name loaded in that tab and carries a close button; click
  switches tabs.
- With one tab open, behavior and chrome match today's single-connection layout
  exactly (tab bar hidden, one chrome, one split tree).

## Expected Outcome

- Multiple tabs run different workspaces and modes simultaneously, fully
  isolated: editing in one tab never mutates another tab's documents, sessions,
  modes, or SDUI/panel/overlay chrome. The tab bar always shows which workspace
  each tab holds.
- Tab structure (order, active tab, per-tab workspace) survives a client
  reconnect (connection drop with the client process alive; and a local
  single-client process restart reclaiming the in-memory server registry) so the
  user does not lose their tab layout to a transient disconnect.
- Single-tab behavior is byte-for-byte the pre-22.3 experience: no tab bar, one
  connection, the existing `ClayShellWidget`/`EditorWidget`/`PaneDocumentView`
  hosting and key paths unchanged.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check
  --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test
  --all-targets`.
