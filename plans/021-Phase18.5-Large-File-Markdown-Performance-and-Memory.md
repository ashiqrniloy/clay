# Phase 18.5: Large-File Markdown Performance and Memory

## Objectives

- Make Markdown typing, scrolling, and visible decoration refresh behave like established native text editors by keeping parser work off hot paths and prioritizing the viewport.
- Replace the current full-document `markdown-it` adapter path for large files with bounded, cancellable, windowed parsing and decoration publication.
- Keep Rust server/client code parser-agnostic and Markdown-agnostic by adding only reusable parse-window, range-snapshot, cache-budget, and decoration-window primitives when required.
- Define and enforce a realistic memory contract for large Markdown files: **not total process RSS below 30 MiB**, which is impossible for Clay's current server-side JavaScript runtime, but **Markdown parsing/decoration overhead at or below 30 MiB above the already-open document and baseline runtime**.
- Preserve security boundaries: no client-side package JavaScript, no raw ops as public APIs, no filesystem/network/shell/AI/WASM authority, no full-document IPC for ordinary edits, and no package work in keypress/paint/scroll/text-event handlers.

## Expected Outcome

- Opening and typing in a 16 MiB Markdown file does not synchronously parse or decorate the full document.
- For large Markdown files, Clay highlights the visible viewport and nearby guard ranges first, cancels stale work, drops off-viewport caches under pressure, and falls back to plain text or partial syntax when budgets would be exceeded.
- For small Markdown files, full-document `markdown-it` parsing remains allowed when it is faster and within memory budget.
- For medium/large Markdown files, `markdown-it` is invoked only on bounded windows/chunks with package-owned absolute range translation; full-document parser benchmarks remain advisory failure evidence, not an interactive path.
- Markdown typing remains local and client-first with p95 local paint at or below the existing keypress budget; background parser delay affects only decoration freshness.
- Markdown parse/decor cache overhead for a 16 MiB file is capped at 30 MiB or less, measured separately from process baseline RSS and canonical document storage.

## Feasibility Statement

A strict requirement that the **whole Clay process** or **server-side JavaScript runtime RSS** stay under 30 MiB is not possible with the current architecture. Fresh measurements on this workstation show a bare Node/V8 process already reports about 46.31 MiB RSS, and the current active Markdown benchmark reports about 147 MiB RSS for a 64 KiB-ish adapter run and about 628 MiB RSS for a 16 MiB full-document adapter run. A 16 MiB document also needs memory for the canonical text/rope, line/layout metadata, undo or edit history, and UI state.

What is possible and should be implemented is a stricter editor-style budget: keep **incremental Markdown-specific parser/decor/cache overhead** under 30 MiB for large files by avoiding full-document token streams, publishing only viewport-bounded spans, and evicting off-viewport chunks.
