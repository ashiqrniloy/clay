# Phase 18.12: Workspace Discovery and File Browser Foundation

## Objectives

- Add server-owned workspace-root discovery from CLI/current directory, opened-file ancestry, explicit user grants, and bounded marker files (`.git`, `Cargo.toml`, `package.json`, and a closed set of known project markers).
- Represent roots with the existing future-compatible multi-root `WorkspaceState` model while shipping a one-root default UI as the smallest working product.
- Add a bounded server file tree/list service with ignore rules, depth/count limits, cancellation, refresh, and diagnostics — without granting arbitrary package filesystem authority.
- Implement a Clay-owned file browser UI: a left fixed panel for tree/list browsing and a bottom transient fuzzy-open workflow for quick navigation.
- Route open/reveal/save-related actions through server-authoritative file/workspace APIs and selected-file grants rather than direct client filesystem access.
- Document Clay JS APIs, configuration hooks, package/user override boundaries, wiki pages, and tests for root discovery, file listing limits, ignored paths, permissions, and UI actions.

## Expected Outcome

- Clay can discover a workspace root, show a browsable file tree, and open files through validated server authority.
- File navigation reuses the same transient menu, command execution, and shell panel primitives as other workflows.
- The implementation is ready for richer file workflows without granting broad client or package filesystem authority.
- All new public programmatic surfaces are exposed as documented Clay JS APIs with generated registry coverage, and the code wiki is updated.

- [x] Add bounded server file tree/list service with ignore rules, depth/count limits, cancellation, refresh, and diagnostics
  - Acceptance Criteria:
    - Functional: A server service lists directory entries under a known workspace root, returning bounded metadata (name, kind, size hint, child count where cheap) suitable for tree/list rendering. It honors ignore rules (a closed, documented ignore source — e.g. `.gitignore`-style at the root, or a Clay-defined ignore list; pick the smallest sufficient), a max depth, a max entry count per request, supports cancellation of in-flight listings, supports explicit refresh, and reports diagnostics (e.g. permission-denied entry, truncated at limit) without failing the whole request.
    - Performance: Listing is paginated/bounded so a huge directory never blocks typing, rendering, or completion. Depth and count limits are named constants with provenance. No recursive full-tree enumeration in a single call. Listing work runs off the Masonry paint/layout/pointer/key path.
    - Code Quality: The service is a generic reusable primitive, not file-browser-specific. Listing results are inert serializable data consumed by SDUI; no client-side filesystem reads. Errors are typed (`WorkspaceError` family) and map to JS errors at the op boundary.
    - Security: Listing is scoped to a known workspace root; paths outside the root canonical boundary are rejected (no traversal escape). Packages cannot list arbitrary paths; only Clay-owned file-browser code and documented Clay JS APIs invoke the service within a granted root. No arbitrary package filesystem authority is introduced.

    - Documentation Reviewed:

      - `.agents/skills/project-patterns/references/authority-boundaries.md`.
