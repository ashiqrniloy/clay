# Phase 20.7: Package UI Conformance and Aesthetic Guardrails

Source: `roadmap.md` → Phase 20.7. Entry gate: Phases 20.2–20.5 (plans 063–066) must define the primitives and components being guarded; Phase 20.6 (plan 067) theme packages exist and are validated through the existing inert path. Do not start until those have landed.

## Objectives

- Guarantee that external (third-party) packages physically cannot inject raw styling, undocumented components/tokens, oversized UI payloads, or token choices that break layout/usability invariants — enforced at server validation time and rechecked client-side before install.
- Extend the existing enforcement points (typed token validation, reserved-kind gating, chrome-paint source guards, editor status-chrome AA contrast) into a complete conformance surface: contrast/legibility checks over SDUI typed-token theme contributions, payload-budget checks for package-contributed components, and state-completeness checks for every catalog kind in every interaction state.
- Ship a package UI conformance test suite that renders every catalog component in every applicable state through structural SDUI observability and validates every theme package for token coverage and fallback correctness, parametric over the active theme.
- Add a CI lint that fails on raw colors/sizes in shell/SDUI paint paths and on undocumented components or tokens (code-vs-catalog drift).
- Give package authors clear diagnostics naming the rejected value, the expected token type, and the offending field, surfaced through the existing server runtime diagnostics channel.
- Document the guardrails in `docs/reference/packages/creating-packages.md` and the `clay-ui` skill so authors and agents can comply without reading paint code.

## Expected Outcome

- A third-party package physically cannot inject raw styling or break layout/usability invariants: invalid contributions are rejected at server validation with an actionable diagnostic and never reach paint/layout.
- Conformance coverage runs in CI alongside existing package tests; `cargo test` fails on raw color/size literals in guarded paint paths, on undocumented/uncataloged components or tokens, on sub-contrast theme packages, on state-incomplete components, and on payload-budget violations.
- Every catalog component is proven renderable in every interaction state through a structural snapshot, for the core theme and every bundled theme package.
- Package authors get named-value/expected-type diagnostics from the same server diagnostics surface already used for runtime errors.
