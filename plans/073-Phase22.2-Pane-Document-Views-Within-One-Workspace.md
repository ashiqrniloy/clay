# Phase 22.2: Pane Document Views Within One Workspace

This plan implements `roadmap.md` Phase 22.2. It turns the Phase 22.1 generic pane hosts (`PaneContentHost` with `PaneContent::Placeholder | Editor`, `src/masonry_pane_host.rs`) into simultaneous document views of the single loaded workspace: each pane independently opens and edits a file, with its own caret/selection/viewport/shadow-sync state, its own active major mode, keyboard routing and status context following pane focus, duplicate file opens blocked within the workspace (the existing pane is focused instead), and all file-open flows targeting the focused pane.

Scope boundary: Phase 22.2 ships **per-pane document views within one workspace** (the single implicit tab owns the split tree and one client connection, as in 22.1). Phase 22.2 does **not** add tabs or per-tab client connections (22.3/22.4), persist pane topology or per-pane open documents across restarts (22.5), or add full accessibility/performance-budget hardening beyond the focused guards listed here (22.6). SDUI sidebar, package fixed panels, and transient overlays remain window/client-scoped chrome in 22.2, not per-pane.

Confirmed architecture decisions (roadmap Phase 22 preamble + Plan 072): each tab owns its split tree (one workspace per tab — in 22.2 the single implicit tab loads exactly one workspace); panes are generic workspace-bound content hosts, never tied to files in the split model; maximum 4 panes per tab; duplicate file opens are blocked within one workspace by focusing the existing pane; server remains authoritative for documents, leases, dirty state, mode activation, and canonical-path identity.

Entry gate: `plans/072-Phase22.1-Equal-Area-Window-Splits.md` must have zero unchecked tasks. Use the current project UI skill requirements before UI design tasks.

## Objectives

- Every pane is an independent document view: multiple files of the one loaded workspace are edited simultaneously, each with its own caret, selection, viewport, and shadow-sync (pending-edit) state via the existing Phase 20 session / `ClientEditQueue` machinery.
- Per-pane major mode activation: panes showing different file types (e.g. `.rs` and `.md`) run their own major modes concurrently with no cross-pane state bleed.
- Pane focus decides keyboard routing and status context.
- Duplicate file opens are blocked within the workspace: opening a file already open in another pane focuses the existing pane instead of creating a second view.
- All file-open flows (native open dialog, file browser, fuzzy open, open-selected-file, open-documents menu) target the focused pane.

## Expected Outcome

- Panes behave as simultaneous file views of a single workspace with correct optimistic-editing sync and no cross-pane state bleed; closing a pane releases its document with the existing dirty-document close semantics.
- The split model stays content-type agnostic: pane↔document mapping lives in the client view layer, so Phase 22.3 tabs and later workspace apps (terminal emulator) mount without changing the split tree.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`.
