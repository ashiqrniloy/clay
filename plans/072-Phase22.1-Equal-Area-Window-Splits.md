# Phase 22.1: Equal-Area Window Splits

This plan implements `roadmap.md` Phase 22.1. It turns the existing structural `PaneSplitTree`/`ClayShellWidget` model (Phase 18.2 / Phase 20.3) into user-facing equal-area window splits: keyboard/mouse-driven split creation, pane close, pane focus, keyboard + pointer resize, pane reordering, and a configurable pane-focus policy — all inside the working area, leaving the fixed `left`/`right`/`top`/`bottom` panel slots untouched.

Scope boundary: Phase 22.1 ships **structural split behavior with generic pane hosts**. New panes show an inert placeholder surface; panes are content-type agnostic and workspace-bound so Phase 22.2 can load per-pane document views and later phases can load workspace apps (e.g. a terminal emulator) without changing the split model. Phase 22.1 does **not** load documents into panes (22.2), add tabs (22.3/22.4), persist pane topology across restarts (22.5), or add accessibility/perf-budget hardening beyond the focused checks listed here (22.6).

Confirmed architecture decisions (roadmap Phase 22 preamble): each tab owns its split tree (one workspace per tab; tabs arrive in 22.3 — in 22.1 the single implicit tab owns the tree); panes are generic workspace-bound content hosts, never tied to files in the split model; maximum 4 panes per tab; every Phase 22 key binding is user-editable through `init.js`.

Entry gate: `plans/064-Phase20.3-Layout-Primitives-Splits-Panel-Resizing-and-Screen-Division.md` must have zero unchecked tasks (Phase 20.3 interactive layout primitives exist). Run `npx ui-skills start` before UI design tasks.

## Objectives

- Split the working area (excluding fixed panel slots) into up to 4 equal-area panes, horizontally or vertically, via two command families: split-the-focused-pane (50/50) and add-equal-pane (redivide the whole working area into N+1 equal areas keeping existing panes in reading order, new pane empty).
- Render clear pane boundaries with existing token-driven chrome (`paint_divider`, `paint_focus_ring`) and host each pane in a generic, stable-identity content widget that later phases can fill with editor views or workspace apps.
- Make every split operation keyboard reachable with user-rebindable bindings through the existing keybinding system, plus pointer support: divider-drag resize (existing Phase 20.3 behavior), click-to-focus, and focus-follows-cursor as a configurable alternative.
- Support keyboard resize and position-move of the focused pane within its tab.
- Enforce the 4-pane cap and equal-area geometry invariants with structural tests.

## Expected Outcome

- Users can split the editor zone into up to 4 equal panes with visible boundaries, add panes that redivide the whole working area equally, close panes, resize panes by keyboard and mouse/trackpad, reorder panes, and move focus between panes entirely from the keyboard, while side/top/bottom panels stay untouched.
- All split commands are bindable from `~/.config/clay/init.js` via the existing `bindKey` facade; the pane-focus policy (click vs cursor) is a documented Clay JS configuration API.
- The pane host is content-type agnostic: Phase 22.2 document views and future workspace apps can be mounted without changing the split tree or shell hosting model.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`.

## Compromises Made

- `Global`-context shell chords route through the editor's key path in 22.1, so they don't fire while a placeholder pane (no editor focus) is active. Accepted: distinct chords avoid editor conflicts today; shell-level Global dispatch is a 22.2+ follow-up.
- Pane topology is not persisted across restarts (`layout.json` still stores only ratio/slot state). Deferred to Phase 22.5 per roadmap.
- Non-editor panes render an empty placeholder surface; per-pane document views arrive in Phase 22.2. The `PaneContentHost` enum shape was designed so that transition is additive.
- `Ctrl+Shift+\` (add equal pane) depends on the platform reporting `\` vs `|` for the shifted backslash; defaults are overridable via `bindKey`, so this is documented rather than solved.
- Bootstrap-message baselines in connection/runtime tests were bumped mechanically for the new `ShellPreferences` handshake message instead of introducing an order-independent drain helper — consistent with the existing caret-style precedent, revisitable if the handshake grows again.
