# Phase 18.11: Completion Provider Framework

## Objectives
- Promote `CompletionTriggerAndResult` from deferred primitive to an implemented, reusable completion provider framework.
- Let behavior manifests declare completion triggers so the client can request completions without running package JavaScript or blocking local typing/rendering.
- Execute completion providers server-side on a UI-reactive, cancellable, versioned, bounded lane with package provenance and permission checks.
- Reuse `TransientMenuSession` for completion display, selection, commit characters, dismissal, accessibility, and status/errors.
- Ship one minimal built-in buffer-word provider to validate the framework without LSP, network, shell, workspace-index, or AI authority.

## Expected Outcome
- Clay has a reusable completion architecture with one working provider and a transient-menu UI that future language packages can consume.
- Completion computation is asynchronous, cancellable, versioned, bounded by `COMPLETION_RESULT_PAYLOAD_BUDGET_BYTES`, and separate from local typing/rendering.
- Package completion providers require explicit `completion-provider` permission and resolver-validated package provenance; disabled/invalid providers degrade to no completion while documents remain editable.
- LSP, AI, workspace-index, snippet expansion, shell/tool execution, and network-backed providers remain later add-ons.
