# Phase 20.4: Core Component Uplift on the Existing Catalog

This plan implements `roadmap.md` Phase 20.4. It restyles every implemented component to the Phase 20.1 minimalist design language using Phase 20.1 tokens and Phase 20.2 chrome primitives, **without changing component kinds, style variables, or token names**, so every existing first-party package (`@clay/markdown`, `@clay/git`, `@clay/rust`, `@clay/typescript`, `@clay/javascript`, LSP bridges, Gruvbox themes) renders correctly without modification.

Scope boundary: Phase 20.4 ships **visual restyling and interaction-state completion** for the existing catalog only. It does **not** add component kinds (Phase 20.5 owns `dropdown`/`collapse`/`modal`/input/menu surfaces), change the shell layout model (Phase 20.3), segregate themes (Phase 20.6), add conformance guardrails (Phase 20.7), or change any `ComponentKind`, typed style variable, `ThemeTokenType`, or core/package token name. New paint helpers are `pub(crate)` internal only.

Entry gate: Phase 20.1 (`plans/062-...md`) and Phase 20.2 (`plans/063-...md`) must have zero unchecked tasks; Phase 20.3 (`plans/064-...md`) is complete. Run `npx ui-skills start` and load the smallest useful UI skill set (redesign/visual) before implementation.

## Objectives

- Route every package-facing component paint path (`editorView` chrome is editor-side; `panel`, `label`, `button`, `list`, `flex`, `stack`, `overlay`, `scroll`, `portal`, `statusItem` are SDUI-side) through the active `ResolvedUiTheme` (`self.ui_theme`) and the Phase 20.2 chrome primitives instead of the core-fallback-only `sdui_theme_style()`, so user theme/design-token overrides actually apply.
- Complete interaction states (`Rest`/`Hover`/`Active`/`Focus`/`Disabled`) for every catalog component, driven by the Phase 20.1 state tokens (`surface.hover`, `surface.active`, `surface.disabled`, `text.disabled`, `accent.primary`, `accent.muted`, `focus.ring`, `opacity.disabled`).
- Apply the minimalist spacing rhythm (4pt scale: `spacing.xxs`/`xs`/`sm`/`md`/`lg`/`xl`/`xxl`) — tight grouping for related elements, generous separation between groups — replacing uniform `panel_padding` everywhere and hardcoded chrome insets in the status bar.
- Uplift `editorView` chrome (caret, selection, scrollbar, diagnostics) to the minimalist aesthetic; make the editor scrollbar reflect `Hover`/`Active` interaction state from pointer hit-testing instead of hardcoded `Rest`.
- Add structural observability snapshots for each component in every interaction state and re-run the full package test suite as a regression gate.
- Preserve the compatibility contract: zero breaking changes for existing packages and themes.

## Expected Outcome

- The whole app reads as one coherent minimalist interface: token-driven colors, state-complete components, rhythmic spacing, near-invisible elevation.
- Package-declared components honor the active user theme (light/dark, Gruvbox, future Modus) because SDUI paint reads `self.ui_theme`, not core fallbacks.
- Every catalog component renders all five interaction states from tokens; disabled components apply `opacity.disabled`.
- The editor scrollbar shows hover/active state; the status bar uses token-driven insets and status colors.
- `cargo test` structural observability covers each component kind in each state; the full first-party package test suite passes without any manifest or style-variable edit.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`.

## Compromises Made

- **Task 3 — spacing rhythm scoped to panel padding + density.** The minimalist spacing rhythm is applied via `panel_padding` reading `spacing.md` × `spacing_scale()` (16px default, density-scaled) and `row_rect`/`paint_text` insets tracking it. Per-element differentiation (`spacing.xs`/`sm` for related-element grouping vs `spacing.md`/`lg` for section separation) is deferred to task 4, where each component's paint is touched for interaction states and the granular spacing belongs. This keeps task 3 focused on the critical active-theme routing gap with one coherent rhythm upgrade rather than a sprawling 45-site per-element rewrite.
- **Task 3 — `depth * 10.0` per-depth indent left as a magic number.** The per-nesting-level `10.0` indent in `row_rect`/`paint_text` is still hardcoded (it is not one of the conformance guard's chrome-size constant patterns, so the guard does not flag it). Token-izing it (e.g. `spacing.xs` per depth) is deferred to task 4 per-component work.
- **Task 3 — `non_test_body` conformance helper fix.** Fixed `non_test_body` to prefer the `mod tests` boundary over the first `#[cfg(test)]`. This surfaced and closed a latent gap (the color/size guards were not scanning `masonry_sdui.rs`/`masonry_shell.rs` paint code). All chrome-paint files verified clean under the corrected scan; no new failures.
- **Task 4 — typed sidebar path has no `disabled`/`selected`.** `paint_node` (the `SduiNodeKind`-typed sidebar file-browser tree) renders Hover/Active/Focus from the shared pointer/focus state but never Disabled, because `SduiNodeKind::Button`/`SduiListItem` carry no `disabled` flag (disabled is a package-declaration concept on `PackageUiComponentTree`/`PackageUiListItem`). The typed path passes `disabled=false`/`selected=false`. Consistent with the catalog; no follow-up needed unless the file browser grows disabled rows.
- **Task 4 — focus is click-to-focus, no Tab traversal.** `focused_action` is set when a package action region is activated by pointer Down. Tab/Shift+Tab navigation between SDUI actions is not implemented (Tab switches panes at the shell level, Phase 20.3). Adding Tab-traversal focus for SDUI components is a follow-up; the state-derivation mechanism already supports it (only the input wiring is missing).
- **Task 4 — container affordance state stays Rest in SDUI paint.** `panel`/`overlay`/`scroll`/`portal`/`flex`/`stack` route chrome through the existing state-complete primitives (`paint_panel_chrome`/`paint_tooltip_shell`) with collapse/resize at `Rest`. The shell manages pane-level focus ring + slot/divider drag state separately (Phase 20.3) and that drag state is not visible to the editor's SDUI paint path. Wiring dynamic collapse/resize `InteractionState` from shell drag state into the SDUI panel chrome is deferred.
- **Task 4 — button Focus fill is `accent.primary`.** Per the plan spec, a focused (un-hovered) button fills with `accent.primary` (a strong accent) plus a focus ring. Phase 20.6 theme packages can tone this down; the mechanism is what task 4 builds.
- **Task 5 — scrollbar thumb-drag scrolling deferred.** Pressing the scrollbar thumb now sets the Active visual state and skips caret placement, but actual drag-to-scroll (thumb follows pointer, page-up/down on track click) is not implemented. The editor scrolls via wheel/keyboard only, as before. The press is a visual no-op besides the Active state. Wiring drag-scroll is a follow-up (the `scrollbar_interaction_state` + `scrollbar_thumb_rect` machinery already exists; only the drag input + scroll math is missing).
- **Task 5 — rest scrollbar reuses `opacity.disabled`.** The minimalist "near-invisible at rest" idiom dims the thumb with `opacity.disabled` (0.55), the only sub-full opacity token, so Rest and Disabled render identically. A dedicated `opacity.scrollbar.rest`/`opacity.scrollbar.hover` token pair is the upgrade path if rest needs to differ from disabled or if theme packages need to tune scrollbar visibility independently (noted via `ponytail:` in `paint_scroll_chrome`).
- **Task 5 — editor chrome size constants unchanged.** `src/editor/surface.rs` keeps `SCROLLBAR_WIDTH`/`SCROLLBAR_MARGIN`/`SCROLLBAR_MIN_THUMB`/`TEXT_INSET` as module constants. The conformance size guard intentionally excludes `surface.rs` (it allows these only in `primitives.rs`/`theme.rs`). Routing editor chrome sizes through `dimension.*` tokens is a larger editor-chrome refactor outside Phase 20.4's restyle-only contract; deferred.
- **Task 6 — status bar insets use `spacing.sm` (12), not `spacing.md` (16).** The plan text mentioned `spacing.md` for the max-width inset, but the plan's own API example (`inset = spacing.sm`, `max_width = width - inset*2`) and the zero-breaking-change restyle contract pointed to `spacing.sm` for both the x-offset and the per-side inset (12 + 12 = 24 total, preserving the prior layout exactly at default density). `spacing.md` (16) would have shrunk the inset and shifted the layout; deferred to a deliberate spacing-rhythm pass if the status bar should tighten. The inset still scales with `spacing_scale()` (compact/spacious).
- **Task 7 — observability helper is test-local, not `pub(crate)`.** The plan offered "a dedicated `pub(crate)` uplift-snapshot helper", but placing `ComponentStatePalette`/`component_state_palette` inside `mod tests` satisfies the intent (no public API, zero runtime cost) with stricter encapsulation and no dead-code surface. If a future phase needs cross-module test access, promoting to `pub(crate)` is trivial.
- **Task 7 — containers + `editorView` have a no-chrome SDUI palette.** `flex`/`stack`/`scroll`/`portal` recurse children and paint no chrome of their own; `editorView` chrome is editor-`StyleRegistry`-driven (task 5), not SDUI state tokens. Their per-state palette is `{fill: None, border: None, text: None}` for all 5 states — honest and complete (the 11-kind × 5-state matrix covers them), but the state coverage for these kinds is verified structurally (Option absence) rather than by pinned color values. Pinning editor chrome colors per state is covered by the task-5 editor scrollbar/caret/selection tests.
- **Task 8 — H1 title kept as "UI Chrome Primitives (Phase 20.2)".** The Phase 20.4 state-color helpers are documented in the intro paragraph and a dedicated section, but the H1 was not renamed (e.g. to mention Phase 20.4) because the existing `phase20_2_primitive_documentation_exists_and_is_linked` test asserts the exact "UI Chrome Primitives (Phase 20.2)" substring. Renaming would require updating that test for no functional gain; the Phase 20.4 content is discoverable via the section heading.
- **Task 9 — no new configuration API; deferral recorded.** Phase 20.4 consumes existing tokens already exposed via `clay.theme.setTheme` (theme-package `designTokens` overrides for density/state/spacing/opacity) and `clay.theme.setTypography` (the `hierarchy.*` custom properties). No new user-facing option was introduced, so no `clay.theme.setDensity`/`clay.ui.setComponentState`/`clay.ui.setSpacingRhythm` API was added. A dedicated per-component density or state-token override API is deferred until a real user-facing setting beyond theme-package `designTokens` is needed.
- **Task 10 — no new public Clay JS API; all helpers `pub(crate)`.** Phase 20.4 is `pub(crate)` paint/interaction work; `component_state_color`/`list_row_fill_color`/`disabled_text_color`/`from_ui_theme`/`typography`/`theme_style`/`ui_theme`/`scrollbar_interaction_state`/`interaction_state` and the pointer/focus setters are all `pub(crate)` or private. The visibility-audit test checks generic words (`typography`/`ui_theme`) for visibility only, not facade presence, since they appear legitimately in `runtime/js/theme.js` prose — exposing them via a facade would still fail the bare-`pub` check.
- **Task 11 — `editor_performance_invariants.rs` `non_test_body` latent gap closed.** The `non_test_body` helper in `editor_performance_invariants.rs` had the same truncation bug fixed in `ui_primitive_conformance.rs` during task 3: it cut `masonry_sdui.rs` at its first `#[cfg(test)] use` import (line 39), so the hot-path source guards were scanning only 38 lines and silently missing all the real paint code. The fix (prefer the `mod tests` boundary) is a strict improvement; existing guards now actually scan the full paint bodies and still pass. A full manual accessibility audit is deferred to Phase 20.7 (structural role/state checks cover this phase).
