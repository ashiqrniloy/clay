# Phase 18.2: Masonry Clay Shell and Pane Runtime Foundation

## Objectives
- Implement a Clay-owned shell/working-area runtime above the editor so `EditorWidget` becomes an editor component instead of the top-level application layout.
- Implement generic `WorkingAreaLayout`, `PaneSplitTree`, and `PaneSlotLayout` runtime foundations from the Phase 18.1 shell/layout architecture gate.
- Preserve editor focus, viewport, caret, status, SDUI composition, behavior-manifest input routing, leases, and responsive client-first editing while the shell owns layout composition.
- Keep Masonry as Clay's internal native widget/layout/rendering substrate, never as a package-facing API.
- Add structural shell observability and deterministic tests for shell root, pane tree, slot layout, split layout, hot-path boundaries, documentation, API/config status, and wiki coverage.

## Expected Outcome
- Clay launches through a Clay shell/working-area root that contains at least one editor pane through the generic pane/slot model.
- The shell can represent a one-leaf pane tree and generic horizontal/vertical split topology without Markdown-specific or package-specific Rust layout branches.
- Leaf pane layout has a mandatory `main` slot and optional `left`, `right`, `top`, and `bottom` slots with Clay-owned sizing, min/max, collapse/visibility, and resize state.
- Existing editor behavior remains responsive: ordinary typing, scrolling, pointer selection, behavior-manifest key routing, edit acknowledgements, SDUI actions, status chrome, and diagnostics still work without package JavaScript or synchronous IPC in Masonry hot paths.
- Package-authoring and primitive docs state which shell/pane/slot behavior is implemented in Phase 18.2 and which package-facing `clay:ui`, panel/component/theme/state/configuration surfaces remain planned for Phases 18.3 and 18.4.
