# Phase 18.21: First-Party LSP Bridge Packages (Rust, TypeScript, JavaScript, Markdown)

Implements `roadmap.md` Phase 18.21 on the completed Phase 18.20 language-intelligence and `language-server` authority foundation. Clay core remains analyzer-neutral: first-party package JavaScript owns LSP 3.17 framing, initialization, synchronization, capability negotiation, position/URI conversion, cancellation, and server policy; Rust owns only generic bounded process, document-event, provider, validation, and publication primitives.

## Objectives

- Ship opt-in `@clay/lsp-rust`, `@clay/lsp-typescript`, `@clay/lsp-javascript`, and `@clay/lsp-markdown` packages.
- Use `rust-analyzer`, `typescript-language-server`, and Marksman as the default Linux server candidates, subject to executable entry-gate verification and recorded versions.
- Map LSP semantic tokens, diagnostics, completion, hover, definition, code actions, and signature help onto existing Clay primitives without LSP types or language branches in core.
- Preserve explicit grant-before-load authorization, exact package/contribution/root provenance, fixed executable/argv, bounded I/O, and trusted-subprocess disclosure.
- Keep Tier 1 Tree-sitter highlighting and base keyword/snippet completion fully usable when no LSP package or executable is available.
- Keep all process, package JavaScript, synchronization, and language-intelligence work asynchronous, cancellable, versioned, bounded, and outside local typing/rendering hot paths.

## Expected Outcome

- Explicitly authorized first-party bridge packages start one fixed language-server contribution per package/workspace root and synchronize server-canonical open documents without blocking local paint.
- Rust, TypeScript, JavaScript, and Markdown receive each server's actually negotiated capabilities through existing Clay semantic-decoration, diagnostic, completion, and language-intelligence paths; unsupported capabilities fail cleanly instead of being simulated.
- Tree-sitter syntax and keyword/snippet completion remain the no-LSP baseline; LSP semantic spans refine syntax additively and LSP completion merges at higher priority unless the user explicitly disables or replaces a base provider.
- Tree-sitter recovery diagnostics overlapping current LSP error/warning diagnostics are suppressed deterministically while unrelated diagnostics remain visible.
- No new filesystem, network, shell, AI, WASM, raw-op, native-widget, client-JavaScript, package-manager, mutating workspace-edit, rename/refactor, formatting, build/test, or import-management authority is granted.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, relevant focused tests, `cargo test --all-targets`, `cargo bench --no-run`, and `git diff --check`.
