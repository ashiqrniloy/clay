# Phase 18.1: Clay Shell, Working Area, and Package UI/Layout Architecture Gate

## Objectives
- Define the Clay-owned application shell, working area, pane/split tree, slot, panel, component, action, state, and style vocabulary before Phase 18.2 implementation begins.
- Document the package-facing boundary above Masonry: Masonry is Clay's native widget/layout/rendering substrate, not a package author API.
- Extend the primitive registry/backlog with reusable shell/layout/package UI primitives for Phases 18.2 through 18.4, without adding Markdown-specific Rust UI branches.
- Update the package authoring guide so future packages and modes have accurate implemented-vs-planned shell/layout guidance.
- Preserve Clay's authority, security, documentation-as-code, configuration-as-API, and hot-path performance constraints while planning shell/layout work.

## Expected Outcome
- Clay has a documented shell/layout/package UI architecture gate that future implementation plans can consume directly.
- `docs/reference/primitives/` records shell/layout primitive targets such as `WorkingAreaLayout`, `PaneSplitTree`, `PaneSlotLayout`, `PanelContribution`, `ComponentContribution`, `TransientOverlayContribution`, `PackageThemeTokenDeclaration`, and package UI/state contribution categories.
- `docs/reference/packages/creating-packages.md` explains the architecture vocabulary, current implementation status, planned APIs, anti-patterns, and examples clearly marked as implemented or planned.
- Tests or deterministic documentation guards fail if the new shell/layout reference docs, primitive rows, backlog rows, package guide updates, docs index links, or wiki links are missing or stale.
- Phase 18.2 can begin with clear Masonry evidence, package-facing boundaries, conflict/precedence rules, and documentation/test contracts.
