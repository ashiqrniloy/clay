# Phase 18.7: Persistent Server Runtime and JS ParseHandler Bridge for Generic Open-Time Mode Activation

## Objectives

- Ship a persistent shared server-side JavaScript runtime whose lifecycle outlives a single module evaluation, so resolver-validated first-party packages can register parse/behavior handlers that persist across document open and edit operations.
- Ship a constrained JS→Rust `ParseHandler` bridge that lets a resolver-validated `@clay/*` package register a real parse callback into `ParseCoordinator::schedule_parse` so `next_update` produces `IncrementalParseUpdate` in production (not only in tests), without accepting arbitrary executable callbacks from user configuration.
- Route selected-file open through the generic package/mode/parse-coordinator path on the persistent runtime, then delete the hardcoded Markdown open path from `src/server/connection.rs`.
- Preserve the deny-by-default authority boundary: no new filesystem/network/shell/AI/WASM/raw-op/native-widget/client-JS/package-enable-disable/package-manager authority beyond the constrained first-party `loadEntry` path already approved in Phase 18.6.
- Establish the persistent runtime foundation that Phase 19 hot-reload semantics depends on.

## Expected Outcome

- Opening a `.md` file no longer spawns a fresh `deno_core::JsRuntime`, copies `packages/markdown/dist` files, writes a generated `init.js`, or removes a temp directory on every open.
- Open-time mode activation and decoration publication route through the generic package/mode/parse-coordinator path on a single persistent server runtime.
- `src/server/connection.rs` has no Markdown-specific branch (`is_markdown_path`, `evaluate_markdown_open`, `create_markdown_open_runtime_root`, `unique_markdown_open_runtime_root`, `markdown_open_init_source`, `markdown_package_is_loaded`, and the Markdown arm of `selected_file_open_followup_messages` are deleted).
- Markdown parser logic lives entirely in `packages/markdown`; no Markdown branches exist in Rust server/client code.
- `ParseCoordinator::schedule_parse` / `next_update` produce `IncrementalParseUpdate` in production from a resolver-validated package handler; `clay.parse.serverRegisterParseHandler` moves from metadata-only to a working registration when backed by the persistent runtime and a validated package.
- Typing/rendering are not blocked by parse work; parse budgets (`maxWindowBytes`, `guardBytes`, `memoryBudgetBytes` ≤ `SYNTAX_CACHE_BUDGET_BYTES`, `timeoutMs` 1..5000) and the `INCREMENTAL_PARSE_UPDATE_BUDGET_BYTES` payload cap are enforced; handler failures surface as typed `ParseCoordinatorError::HandlerFailed`; the `JS_RUNTIME_EVALUATION_TIMEOUT_MS` / `clay.runtime.timeout` guard still applies.
- A second mode (future Python/JSON) can be added by writing a package on top of the generic primitives with no new Rust mode branches.
- Security boundary tests enforce deny-by-default for arbitrary executable handler registration, arbitrary specifiers, and authority expansion through the load path.
- Decision log records the authority expansion (long-lived runtime holding package closures; JS on the edit/open hot path).
