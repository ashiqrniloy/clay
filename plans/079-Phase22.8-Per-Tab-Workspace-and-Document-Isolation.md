# Phase 22.8: Per-Tab Workspace and Document Isolation

Prerequisite: Plan 078 (Phase 22.7 — Window Split and Tab Cleanup and Hardening) completes first. This plan builds on its extracted driver modules, hardened shell invariants, bounded registry, and documented connection-owner contract.

This plan implements the workspace/document isolation that `roadmap.md` Phases 22.3, 22.5, and 22.6 already promised but the server never built. Today the server holds ONE shared `WorkspaceState` (workspace roots + open documents) and ONE shared welcome `DocumentState` for the entire process (`src/server/mod.rs:446-448`). Every tab connection shares them. The result (user-reported): a new tab always displays the folder the server started in, never the folder the user selected for that tab; the tab card name (from the registry's `workspace_root`) disagrees with the visible files (the shared workspace); and workspace roots leak across tabs.

Scope boundary: Phase 22.8 ships **per-tab workspace + document isolation on the server** (state keyed by `TabId`, connection routing, handshake ordering), the matching **client integration** (new-tab/restore/reconnect consume the tab's own workspace), and two user-requested workspace-panel behaviors: a **toggleable workspace (file browser) pane that defaults to hidden**, and a **workspace identity header showing the folder name and location**. It explicitly does NOT redesign the split-tree model, the tab registry schema beyond the routing key, the package runtime trust domains, or the SDUI/theme/typography ownership (those remain global in 22.8 unless a task says otherwise). Per-file document isolation and multi-document splits ALREADY work and must be preserved, not rebuilt (see Objectives).

Confirmed architecture decisions (roadmap Phase 22 preamble + Plans 073/074/076/077):
- Each tab is a real separate client connection with independent workspace roots, open documents, and active modes, isolated from other tabs (roadmap Phase 22.3).
- Each tab owns its split tree and per-pane state — one workspace per tab (roadmap Phase 22.5).
- Per-tab workspace grants and package scopes cannot leak across tabs (roadmap Phase 22.6 authority review).
- Server remains authoritative for canonical documents, versions, transactions, leases, dirty state, workspace/file authority, and the tab registry (planning-checklist server-authority).

What ALREADY works and must be preserved (verified against code, not assumed):
- Per-file document isolation: `WorkspaceState.documents: HashMap<DocumentId, OpenDocument>` where each `OpenDocument` owns its own `Arc<Mutex<DocumentState>>` (rope, lease, version, dirty, region locks, access holders) — `src/server/workspace.rs:240-244`. Edits route by `document_id` via `document_for_message` and fall back to the shared welcome document only when the id is not an open workspace document — `src/server/connection.rs:document_for_message`.
- Multi-document splits within one workspace: Phase 22.2 per-pane document views (`MAX_PANES_PER_TAB = 4`, `src/shell/layout.rs:21`), per-document client sessions (`DocumentSessionStore`, `src/editor/document_session.rs`), per-document edit sync (`ClientEditQueue`, `src/client/mod.rs`), per-document mode activation (`active_major_modes: DocumentId → MajorModeActivation`, `src/packages/modes.rs`). So the user's requirement "multiple documents viewed in different window splits within a tab" is implemented and must survive isolation.
- Tab registry: per-tab identity/order/active + `workspace_root` + client binding + monotonic revision, with `Reclaim` rebinding across reconnects — `src/server/tab_registry.rs`.
- File browser surface (partially wired, verified against code): `FileBrowserState` + `to_sdui_tree` (`src/shell/file_browser.rs`) build the left sidebar tree; the server sends it via `SduiSnapshot` at handshake and after workspace mutations (`file_browser_snapshot_message`, `src/server/connection.rs:2312`); the client renders it as a sidebar inside the editor region of the EditorWidget holding the tree (`sidebar_geometry`, `src/masonry_sdui.rs:379`; `src/masonry_editor.rs:1134`). The command `clay.workspace.toggleFileBrowser` is registered, allowlisted for keybinding (`src/server/ops/keybindings.rs:347`), and bound in the `file-browser-workflow` fixture as `Ctrl+B`, but its server handler is a NO-OP stub (`src/server/command_execution.rs:298`) — no visibility state exists. The sidebar header renders only `Workspace · {display_name}` (`src/shell/file_browser.rs:150`); the root metadata already carries the full `display_path` (`src/server/workspace.rs:95`) but does not show it.

Entry gate: `plans/077-Phase22.6-Hardening-Accessibility-and-Documentation.md` must have zero unchecked tasks. Run `npx ui-skills start` before the split/pane verification task.

## Objectives

- Each tab loads and isolates its own workspace: opening a new tab with folder `X` shows `X`'s file tree and documents, not the server startup folder and not any other tab's roots.
- Workspace roots do not leak across tabs: adding/selecting a root in one tab never changes another tab's visible roots or file browser.
- Tab card name and visible content agree: both derive from the tab's own workspace root.
- Multi-document splits within a tab keep working under isolation: each pane of a tab opens/edits a different file from that tab's workspace with per-document lease/version/dirty/mode state (the Phase 22.2 behavior, now scoped per tab).
- Reconnect/restore rebind a tab to its own workspace state (server restart and connection drop both converge), consistent with the existing `Reclaim` semantics and the registry revision gate.
- Server authority preserved: documents, leases, versions, dirty state, and workspace/file grants stay server-owned and per-tab; no cross-tab authority leak.
- Workspace pane (file browser) is user-controlled: a key binding toggles it on/off per tab, it defaults to OFF (hidden), and document opening stays fully possible while hidden (existing `Ctrl+O` file dialog / fuzzy-open).
- The workspace pane header identifies the loaded workspace by folder name AND location (full path), not name only.

## Expected Outcome

- A fresh `clay` + `Ctrl+T` (or `+`) selecting folder `X` opens a tab whose file browser and documents are rooted at `X`; the tab card reads `X`; a second tab selecting folder `Y` is independent (no root/content bleed either direction); closing one tab does not disturb the other's workspace.
- Within any tab, splitting (`Ctrl+\` / `Ctrl+-`) and opening different files in each pane edits them concurrently with independent caret/selection/version/dirty/mode state.
- Client restart restores each tab's own workspace + split tree + per-pane documents; connection drops reconnect to the same per-tab state.
- On launch the workspace pane is hidden; pressing the toggle binding (default `Ctrl+B`) shows the pane with a header naming the workspace folder and its full location (e.g. `clay` + `/home/arn/Projects/clay`); pressing it again hides the pane; each tab toggles independently; documents can still be opened while hidden via `Ctrl+O` (or fuzzy-open when bound).
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`.
