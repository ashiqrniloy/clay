# Phase 18.4: Package Input, Actions, State/Data, and Configuration Integration

## Objectives
- Complete the package-facing structure around Phase 18.3 slot-aware UI by standardizing package input interests, component-scoped actions, focus scopes, data/state scopes, and user/package configuration defaults.
- Promote the remaining Phase 18.4 shell/package UI primitives (`PackageUiStateScope` and `PackageLayoutOverride`) through documented Clay JS APIs only when validators, docs, generated registry coverage, tests, and package-authoring guidance exist.
- Preserve behavior manifests for client-first predictable text/key behavior while routing side effects, UI actions, file/workspace actions, and package actions through server/client command intents.
- Define deterministic user/package override precedence for package defaults, package options, layout/panel visibility, input/action defaults, and theme token remaps through `~/.config/clay/init.js` Clay JS APIs rather than hidden keys.
- Keep package JavaScript, package validation, configuration evaluation, raw IPC waits, and native widget mutation out of Masonry paint/layout/pointer/scroll/key/text-event hot paths.

## Expected Outcome
- Package authors have one coherent implemented model for UI, input, actions, logic, data/state, configuration, and styling, with clear implemented-vs-deferred status.
- Packages can declare non-key input interests, component-scoped action/focus metadata, state/data scopes, and layout/panel/theme defaults as bounded inert data validated by Clay.
- Users can configure supported package defaults and workflows through documented Clay JS APIs from `~/.config/clay/init.js`; hidden JSON/TOML/ad hoc layout/style/input keys remain rejected.
- Tests cover package contribution validation, user override precedence, state-scope validation, behavior-manifest compatibility, command/action routing, configuration docs/registry coverage, package-guide accuracy, and hot-path boundaries.
