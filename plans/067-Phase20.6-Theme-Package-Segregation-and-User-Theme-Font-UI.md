# Phase 20.6: Theme Package Segregation and User-Configurable Theme/Font UI

Source: `roadmap.md` → Phase 20.6. Entry gate: Phase 20.1 token expansion (plan 062) and Phase 20.5 input components (plan 066) must exist; settings UI is built exclusively from catalog components.

Pinned light/dark selection semantics (decided here, per roadmap instruction):

- A new bounded `appearance` preference: `"light" | "dark" | "system"` (default `"system"`). `"system"` follows the OS/desktop color-scheme signal Clay can observe at startup and on change; if no signal is available it resolves to dark.
- `appearance` selects the *canonical default theme* only: light → `@clay/theme-modus-operandi`, dark → `@clay/theme-modus-vivendi`.
- An explicit theme specifier (`setTheme("@clay/theme-…")`) always wins over `appearance`-derived selection, including Gruvbox packages.
- Precedence (low → high): package defaults < `~/.config/clay/init.js` user config < UI session changes. UI session changes apply live and are persisted to the user config store so they survive restart; the persisted value is written as ordinary `init.js`-equivalent configuration, not a hidden store.

## Objectives

- Ship Modus Operandi (`@clay/theme-modus-operandi`) and Modus Vivendi (`@clay/theme-modus-vivendi`) as segregated inert theme packages, canonical light/dark defaults, alongside existing optional Gruvbox packages, preserving upstream naming, provenance, licensing/attribution, and accessibility intent.
- Make theme, font role, and font-size-hierarchy configuration user-facing from a settings UI built only from catalog components, with `init.js` override and documented precedence.
- Live theme/appearance/typography switching without restart, typography revalidated through the existing revisioned typography registry.
- Document theme authoring and user override APIs; keep generated Clay JS API registry coverage current.

## Expected Outcome

- Users switch and tune themes, fonts, and the title/text size hierarchy from the settings UI or `~/.config/clay/init.js`.
- Modus Operandi is the canonical light default and Modus Vivendi the canonical dark default, both bundled first-party packages resolved through the same inert path as Gruvbox.
- Appearance follows system unless the user pins a theme; explicit theme choice wins; changes apply live and persist.
