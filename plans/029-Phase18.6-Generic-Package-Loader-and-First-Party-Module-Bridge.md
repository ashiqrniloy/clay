# Phase 18.6: Generic Package Loader and First-Party Module Bridge

## Objectives
- Ship the constrained generic `loadPackage("@clay/*")` specifier resolver, the first-party `ClayModuleLoader` extension, the `PackageService` resolve/validate/enable/return-`loadEntry` path, and the `clay:packages.loadPackage` facade that Phase 18.5 Task 4 deferred.
- Make `import { loadPackage } from "clay:packages"; await loadPackage("@clay/markdown");` work end-to-end from `~/.config/clay/init.js` as a one-line default with no inline manifest, no copied fixture metadata, and no manual primitive registration.
- Land the resolver, the module-loader bridge, the op, and the facade as one coherent, security-reviewed authority-expansion unit with its own decision log, not as incremental patches to Markdown or hot-reload phases.
- Preserve the deny-by-default module boundary for arbitrary specifiers, external packages, registry fetching, package-manager execution, and authority-expanding imports: only resolver-validated first-party `@clay/*` `loadEntry` modules may load from outside the configuration root.
- Transition the `!one_line_loader_is_implemented` test assertion to verify `loadPackage` is now a working `clay:packages` export, and update Plan 023 to assume the generic loader from the start.

## Expected Outcome
- `import { loadPackage } from "clay:packages"; await loadPackage("@clay/markdown");` works end-to-end from `~/.config/clay/init.js` as a one-line default.
- The controlled server-side runtime can load resolver-validated first-party package `loadEntry` modules from outside the configuration root, but the module boundary remains deny-by-default for arbitrary specifiers, external packages, and authority-expanding imports.
- `PackageService` resolves, validates, enables, and returns package `loadEntry` paths for `@clay/*` packages, and the JS runtime executes the declared `loadEntry` under Clay's authority without granting general filesystem, registry, or package-manager access.
- The `tests/package_loading_docs.rs` gap test transitions from asserting the loader is unimplemented to asserting `loadPackage` is a working `clay:packages` export with `status = "runtime-backed"` and `registry_public = true`.
- Plan 023 is updated so every task, acceptance criterion, and example assumes `loadPackage("@clay/markdown")` works from the start; the package-owned `markdownLoadMode()` fallback and the fixture-style `serverLoadPackage(packageJson)` setup become fallback/test-only paths.
- No new filesystem, network, shell, AI, WASM, raw-op, native-widget, client-JS, package-enable/disable, or package-manager execution authority is granted beyond the constrained first-party `@clay/*` load path.
- A decision log records the authority expansion with explicit approval, the deny-by-default boundary, the constrained `@clay/*` allowlist, the upgrade path for future non-`@clay/*` packages, and the security review.
