# Phase 20.1: UI Design Language, Token Catalog Expansion, and Typography Hierarchy

This plan implements `roadmap.md` Phase 20.1. It extends existing Clay-owned theme and typography primitives; it does not restyle every component or add new component kinds. Component uplift remains Phase 20.4, primitives remain Phase 20.2, and settings UI remains Phase 20.6.

Default-theme boundary: Phase 20.1 keeps `@clay/default` as a safe core fallback and prepares typed values needed by complete themes. Phase 20.6 will ship the exact canonical pair requested by the user: **Modus Operandi** (`@clay/theme-modus-operandi`) for light mode and **Modus Vivendi** (`@clay/theme-modus-vivendi`) for dark mode. Gruvbox Material Light/Dark remain optional shipped themes. Phase 20.1 must not implement a competing default pair or silently change light/dark selection semantics. The [official Modus manual](https://protesilaos.com/emacs/modus-themes) identifies `modus-operandi` as the main light theme and `modus-vivendi` as its dark counterpart; Phase 20.6 must verify palette provenance and licensing before porting values.

UI skill selection recorded for this phase:

- `leonxlnx/minimalist-skill`: restrained palette, crisp radii, near-invisible elevation, scarce accent color.
- `leonxlnx/redesign-skill`: preserve current native architecture and functionality; make targeted, additive improvements rather than rewrite UI.
- `pbakaus/layout`: use a 4pt spacing scale, proximity-based grouping, deliberate tight/generous rhythm, and token-backed density.

Clay translation: these web-oriented skills inform native Masonry/Vello/Parley tokens and semantics only. Clay has no CSS/Tailwind, packages receive no renderer access, and the catalog in `.agents/skills/clay-ui/references/` remains authoritative.

## Objectives

- Define one restrained, modern minimalist design language as typed Clay tokens with additive names and same-typed fallbacks.
- Expand spacing, radius, state color, focus, border, elevation, motion, overlay level, density, and layout-dimension tokens needed by Phases 20.2–20.7.
- Expand `UiTextVariant` beyond `Title`/`Body`/`Status`/`Detail` with `Display`, `Section`, and `Caption`, while preserving user ownership of font profiles and hierarchy scales.
- Replace hardcoded default panel/sidebar dimensions and density assumptions with resolved tokens without implementing Phase 20.3 resize/persistence behavior.
- Preserve current theme packages, component kinds, style-variable names, server/client authority, accessibility geometry, and hot-path behavior.
- Keep token/component catalogs, package authoring docs, Clay JS API docs, generated registry, and code wiki synchronized.

## Expected Outcome

- Later UI uplift phases can obtain every approved color, spacing, radius, border, elevation, motion, z-level, density, panel default, and typography level from a typed client-side registry.
- Existing token names and Gruvbox theme packages continue to validate and render unchanged through core fallbacks; no package migration is required.
- UI text supports `Display`, `Title`, `Section`, `Body`, `Status`, `Detail`, and `Caption` variants resolved from user-configured semantic font profiles and bounded hierarchy scales, never package-supplied font families or point sizes.
- Legacy fixed sidebar and package-panel defaults read one token-backed geometry source; Phase 20.3 can add resize/persistence without replacing defaults again.
- Ordinary typing, paint, layout, pointer, scroll, keypress, and text-event paths perform no package JavaScript, server round trip, filesystem/network work, or repeated theme parsing.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, and `cargo test --all-targets`.
