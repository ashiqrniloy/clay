# Phase 22.4: Keyboard Tab Management

This plan implements `roadmap.md` Phase 22.4. It adds full keyboard control of
the Phase 22.3 tab model: default key bindings for view-tab-by-number (1..9),
next/previous tab, new tab, close tab, move tab left/right, and move tab to a
specific position; user-rebindability of every Phase 22 key binding (tab and
split commands alike) through `init.js` via the existing keybinding system
(`clay:keybindings` `bindKey`/`unbindKey`); tab command IDs registered with
correct routing policies and listed in the command/help surfaces; explicit
policies for tab-count bounds, numbered switch beyond 9, and next/previous
wraparound; and the close-tab confirm/save flow for dirty documents
(consistent with the existing document-close save-conflict behavior).

Architecture: all tab operations remain **server-authoritative in their
registry effects** — the Phase 22.3 `TabRegistry` (order, active tab, per-tab
workspace + client binding) stays the single source of truth; the server gains
reorder operations (`MoveLeft`/`MoveRight`/`MoveTo` on `TabCommand`), and every
mutation (including rejections) pushes a `TabRegistry` snapshot that the
client's `apply_registry_reconcile` applies. The client executes the
keybindings: numbering maps positions in the latest snapshot/card order to
tabs, switching is optimistic (existing `switch_tab` + `Activate` reconcile
pattern), and moves/close are server-confirmed like the 22.3 close path. No
new keybinding machinery is needed — the Phase 22.1 `KeyBindingRule::global_client_ui`
(`KeyBindingContext::Global`, `RoutingPolicy::ClientUiCommand`) pattern, the
`default_keymaps()`/`default_commands()` tables, the `bindKey` allow-lists, and
the `ShellClientCommand` dispatch path all extend additively. New command IDs
follow the Phase 22.1 pane-command naming (`clay.shell.clientTab*`) and the
dotted-variant family precedent (`clay.editor.clientMoveCursor.nextWordStart`
style) for the numbered families.

Scope boundary: Phase 22.4 ships **tab command IDs + default key bindings +
rebindability + bounds/wraparound policies + the dirty-close confirm/save
flow**. It does **not** persist the tab registry or per-tab split trees/per-pane
documents to disk (22.5), add full accessibility roles/announcements,
performance budgets, or the cross-tab authority review (22.6), add mouse-drag
tab reorder (not in the roadmap; keyboard move only), add multi-client tab
reclamation (Phase 21), or add keyboard focus traversal inside the tab bar
(bar focus/arrow-key card traversal is 22.6 accessibility; 22.4 drives tab
operations by command, not by focusing cards).

Confirmed architecture decisions (roadmap Phase 22 preamble + Plans 072/073/074):
each tab owns its split tree (one workspace per tab); each tab is a real
separate client connection with server-authoritative tab state; panes are
generic workspace-bound content hosts; maximum 4 panes per tab; every Phase 22
key binding is user-editable through `init.js`. Authority: server owns the tab
registry (order/active/binding) and validates every `TabCommand` (bound client,
existing tab, position bounds); client owns rendering, focus, optimistic
switch, and the close dirty-guard/confirm flow.

Entry gate: `plans/074-Phase22.3-Tabs-as-Independent-Client-Views-with-Tab-Bar.md`
must have zero unchecked tasks. Run `npx ui-skills start` before UI design tasks.

## Objectives

- Default key bindings for every Phase 22.4 tab operation: view tab by number
  (1..9), next/previous tab, new tab, close tab, move tab left/right, move tab
  to a specific position — plus every existing Phase 22.1 split/pane binding —
  all user-editable through `init.js` via the existing `clay:keybindings`
  system (bind/unbind overrides, deny-by-default validation unchanged).
- Tab command IDs registered with the correct routing policy
  (`RoutingPolicy::ClientUiCommand`, `KeyBindingContext::Global`) in
  `default_commands()`/`default_keymaps()`, the `bindKey` allow-lists, the
  client dispatch path, and the command/help surfaces (behavior-manifest
  command declarations, Clay JS API docs, `api-inventory.toml`, generated
  registry, `docs/index.md`).
- Explicit, documented policies: numbered switch beyond 9 (unreachable — only
  1..9 exist; numbers beyond the current tab count are no-ops), wraparound for
  next/previous (last → first, first → last), no-wraparound for move left/right
  (boundary is a no-op), last-tab close protection (existing 22.3 gate), and
  server-validated move positions.
- Close-tab safety for dirty documents: a tab-level confirm/save flow
  (save-all-and-close / discard-and-close / cancel) consistent with the
  existing document-close save-conflict behavior, replacing 22.3's plain
  dirty-block guard.

## Expected Outcome

- Every tab operation — switch by number, next/prev, new, close, move — is
  reachable from the keyboard with sane defaults, and every Phase 22 binding
  (tab and split) is rebindable in `~/.config/clay/init.js` with
  `bindKey`/`unbindKey`, with the deny-by-default unknown-command validation
  intact.
- Tab structure (order, active tab) stays server-authoritative: numbered
  switch, next/prev, and moves all reconcile against server-pushed `TabRegistry`
  snapshots, so optimistic switch and rejected mutations behave exactly like
  the 22.3 activate/close paths.
- Closing a tab with unsaved edits always offers Save all and close / Discard
  and close / Cancel; no edits are ever dropped silently (22.3's block guard is
  upgraded, not weakened).
- Linux blocking validation passes: `cargo fmt --check`, `cargo check
  --all-targets`, `cargo clippy --all-targets -- -D warnings`, `cargo test
  --all-targets`.
