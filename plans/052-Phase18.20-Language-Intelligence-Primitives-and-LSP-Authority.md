# Phase 18.20: Language Intelligence Primitives and LSP Authority

Implements `roadmap.md` Phase 18.20 and the opt-in LSP direction approved in `decision-logs/2026-07-09-0352-tiered-tree-sitter-themable-syntax-vocabulary-theme-registry-and-opt-in-lsp.md`. Clay core will own engine-neutral language-intelligence requests, validated inert results, UI projection, and a permissioned process boundary; LSP protocol mapping and language-specific server choices remain package work for Phase 18.21.

## Objectives

- Add engine-neutral hover, definition, code-action, and signature-help primitives using Clay document versions, UTF-8 byte ranges, package provenance, cancellation, and bounded payloads.
- Activate semantic-intelligence publication through the existing additive `DecorationKind::Semantic` path while reusing existing diagnostics and completion primitives.
- Add a dedicated, deny-by-default `language-server` package capability and explicit user grant from `~/.config/clay/init.js`.
- Add one generic, async language-server process/session boundary with fixed validated package declarations, known-workspace cwd, capped I/O, timeouts, cancellation, and sanitized diagnostics.
- Keep LSP types, JSON-RPC framing, server-specific launch policy, and language-specific branches out of Clay core.
- Preserve immediate local typing/rendering and keep all intelligence/process work on cancellable UI-reactive or background lanes.

## Expected Outcome

- A generic analyzer fixture can provide hover, definition, code-action, signature-help, semantic-token, diagnostic, and completion results through Clay primitives without any LSP dependency or language-specific Rust branch.
- User actions can request and display hover/signature help, list definitions/code actions, navigate validated definition locations, and execute only already-authorized command-backed actions; direct code-action edits remain inert previews in this phase.
- A package cannot start a language-server session unless it declares `language-server`, the user grants the exact package/server contribution and workspace scope before package execution, and the runtime validates package provenance.
- Language-server processes use direct `tokio::process::Command` execution, never a shell or package-provided runtime argv, and are killed/cleaned up on timeout, package withdrawal, runtime reload, or server shutdown.
- Phase 18.21 can implement `@clay/lsp-*` packages by mapping LSP 3.17 responses onto these primitives without adding LSP code to Clay core.
- Linux blocking validation passes: `cargo fmt --check`, `cargo check --all-targets`, `cargo clippy --all-targets -- -D warnings`, relevant tests, `cargo test --all-targets`, and `cargo bench --no-run`.
