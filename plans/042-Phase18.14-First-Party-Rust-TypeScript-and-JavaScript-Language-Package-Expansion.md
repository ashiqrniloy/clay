# Phase 18.14: First-Party Rust, TypeScript, and JavaScript Language Package Expansion

## Objectives

- Revisit `@clay/rust`, `@clay/typescript`, and `@clay/javascript` as consumers of existing Clay primitives before adding any new Rust code.
- Add language-specific mode declarations and user-visible behavior only where existing generic primitives justify it: indentation parameters, comment toggles, structural commands, completion trigger metadata, status items, and package configuration.
- Keep all language behavior on generic primitives: behavior manifests, command declarations/execution, syntax grammar contributions, decoration ranges, completion providers, transient menus, package UI, and configuration APIs.
- Prove that first-party language packages can graduate from grammar-only packages to fuller modes without changing the package-provided syntax architecture or adding Rust language branches.
- Document and test the expanded packages, update generated registry entries and wiki coverage, and measure fallback behavior when packages are disabled or invalid.

## Expected Outcome

- `@clay/rust`, `@clay/typescript`, and `@clay/javascript` become first-party language packages built on generic Clay primitives, not hard-coded editor modes.
- Each package loads from `~/.config/clay/init.js` with a one-line `loadPackage("@clay/<lang>")` call and contributes a documented major mode, grammar, key behavior, commands, and optional status/configuration surfaces.
- Opening `.rs`, `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, or `.cjs` files selects the package's major mode through generic document classification, attaches the package-provided syntax grammar, and applies package-declared behavior manifests.
- Language-specific commands such as toggle comment, insert language-specific block, or format-document-stub are routed through the generic `CommandExecutor` path with package provenance and permissions.
- Completion triggers and a minimal buffer-word/language-keyword provider are wired through the generic completion framework where the framework exists.
- Disabled, invalid, or missing packages fall back to `core.code`/`core.text` with grammar highlighting detached.
- All public programmatic surfaces are documented Clay JS APIs with generated registry coverage; no new Rust public function is exposed without an op wrapper, facade, docs, and registry entry.

## Compromises Made

- **No user-tunable configuration in Phase 18.14.** Indent size, comment tokens, delimiter pairs, and autocomplete triggers are package-defined defaults. Customization is deferred to a future phase that will use package-prefixed `clay.contributions.packageOptions` entries read through `clay.configuration.setPackageOption`. This keeps the phase focused on generic primitive integration rather than adding a new configuration-read path before the existing configuration runtime is fully wired.
- **Metadata-only completion providers.** The `rust.keywords`, `typescript.keywords`, and `javascript.keywords` providers register trigger characters and budgets but do not yet return real keyword lists. The generic completion framework supports provider results; populating actual language keywords requires additional design for static keyword tables versus dynamic provider results and is deferred.
- **Inert status-item declarations only.** The `<lang>.status.mode` components are validated UI contributions; no live status update wiring or SDUI status-region integration was added in this phase. The shell already owns status chrome, so the package declarations can be rendered once the shell status region consumes registered component contributions.
- **Smoke fixture does not auto-activate modes.** The `tests/fixtures/configuration/language-packages/init.js` fixture loads all three packages but stops before calling `serverActivateClassifiedMode`. Attempting to activate from the fixture hit an `UndeclaredMode` error because the package manifest captured in the mode activation registry (passed to `serverRegisterModePattern`) is not the same validated/enabled package record used by major-mode activation validation. Mode classification and activation are already covered by dedicated integration tests; the fixture is documented as a one-line load entry that the user extends by opening files.
- **Hardcoded facade source strings.** `buildCodeEditingManifest` and `completionTriggerCharactersFromEditorRules` are implemented both in `runtime/js/*.ts` and in the inline `CLAY_FACADE_*` strings in `src/server/js_runtime.rs` because the server runtime currently injects facade modules as static strings rather than compiling the TypeScript sources dynamically. This is consistent with the existing `clay:behavior` and `clay:completion` facades but means helper changes must be mirrored in two places.

## Further Actions

- **Populate real completion item payloads.** Once the completion framework stabilizes, replace the placeholder `rust.keywords`/`typescript.keywords`/`javascript.keywords` providers with bounded keyword tables or lightweight symbol sources. Priority: medium; blocked on finalizing `CompletionResult` payload shape and provider result caching.
- **Per-language user configuration.** Add package-prefixed options (e.g., `rust.indentSize`, `typescript.tabSpaces`) declared in `clay.contributions.packageOptions` and read through `clay.configuration.setPackageOption`. Priority: medium; depends on Phase 18.4 configuration read APIs being runtime-backed.
