# Existing Primitive Audit

This audit identifies the primitive surfaces already present before Phase 16 across behavior manifests, SDUI, configuration, file/workspace, document editing, and observability. It is a static analysis artifact only: it adds no runtime primitive, protocol message, op wrapper, or hot-path code.

## Sources Reviewed

- `roadmap.md` Phase 16 primitive architecture goals.
- `docs/reference/clay-js-api/api-inventory.toml` for current Clay JS API IDs, authority, hot-path policy, permissions, documentation paths, and implementation owners.
- `src/protocol/mod.rs` for document, edit, behavior, file/workspace, runtime diagnostic, and protocol message primitives.
- `src/behavior/manifest.rs` for manifest validation and security boundaries.
- `src/protocol/sdui.rs` and `src/server/sdui.rs` for SDUI node/update/action primitives and validation.
- `src/server/document.rs` and `src/server/workspace.rs` for server-canonical document, lease, region lock, file, and workspace primitives.
- `src/perf/budgets.rs`, `docs/development/performance.md`, and `docs/development/ui-observability.md` for payload/latency budgets and Phase 14/15 observability surfaces.
- `.agents/skills/project-patterns/references/behavior-manifests.md` and `.agents/skills/project-patterns/references/authority-boundaries.md` for routing and server/client ownership rules.

## Audit Legend

- **Owner** is the component that owns the canonical primitive definition or state.
- **Authority boundary** states what can mutate or publish the primitive.
- **Hot-path classification** uses the closest existing vocabulary from `api-inventory.toml`, manifest routing policies, and `src/perf/budgets.rs`.
- **Permissions** lists current inventory permissions. `none` means inert data or client-local state with no external authority.
- **Coverage status** cites existing test/doc coverage where known.

## Security and Permission Findings

Existing primitives fall into two broad classes:

1. **Permission-bearing server authority**: document mutation (`document-edit`), document reads (`document-read`), workspace reads (`workspace-read`), and workspace writes (`workspace-write`). These are represented by editor/document/workspace Clay JS API stubs or runtime-backed APIs in `api-inventory.toml` and must be server-validated before they mutate or reveal canonical state.
2. **Inert declarations or client-local metadata**: behavior manifests, keybinding declarations, SDUI node helpers, SDUI action intents, configuration metadata, client cursor/selection/viewport state, runtime diagnostics, and performance/structural observability. These carry no current permission because they do not themselves grant filesystem, network, shell, extension loading, AI mutation, WASM, raw op, native widget mutation, or client-side JavaScript authority.

Important boundary notes:

- Behavior manifests deliberately contain no executable JavaScript field. `src/behavior/manifest.rs` rejects routing/authority combinations that would let side-effectful server intent masquerade as `ClientFirstPredictable` built-in client edits.
- SDUI helpers produce inert typed object graphs. `src/server/sdui.rs` validates tree shape, editor bindings, update versions, and action source/command consistency before publication or action handling.
- Configuration JavaScript runs server-side through the constrained runtime and can load only relative local `.js` files under the configuration root. It is not a package loader, workspace scanner, network fetcher, shell runner, or client-side script hook.
- File/workspace primitives are already server-authoritative and path-validated. Unauthorized paths are sanitized in diagnostics.
- Observability primitives must remain sanitized. Phase 14/15 docs explicitly prohibit recording document contents, secrets, absolute user paths, network listeners, shell authority, or arbitrary client JavaScript.

## Existing Coverage Gaps Relevant to Later Phase 16 Tasks

- There is no existing document classification or mode detection primitive for file extensions/MIME types.
- There is no existing major/minor mode activation registry beyond `BehaviorScope::Language` and document/global manifest scope placeholders.
- There is no existing inline decoration range, semantic token, diagnostic span, folding range, or block/inline render-intent primitive.
- There is no existing incremental parser/background parse task primitive or parse result publication message.
- There is no package-owned command registration API; current `CommandDeclaration` is a manifest data type and runtime keybinding can only bind documented existing commands.
- Existing SDUI covers panels/widgets/editor views but not span-level editor rendering customization.
- Existing performance budgets cover edit, manifest, SDUI, runtime configuration, scroll/render, and memory surfaces, but not decoration payloads, incremental parse payloads, completion result payloads, folding payloads, or mode activation latency.
