# Clay Primitive Registry Schema

Version: `phase16-primitives-v1`

This registry defines the first exhaustive-but-iterative taxonomy for primitives that Clay packages may contribute. It is an architecture document only: entries marked `New` or `Planned` describe the public Clay JS API shape and validation contract that later phases must implement.

## Registry Schema

Every primitive category entry uses the same vocabulary as `docs/reference/clay-js-api/api-inventory.toml` so future TOML/code-generation work can derive from this document without renaming fields.

| Field | Meaning |
| --- | --- |
| `primitive` | Stable primitive category name. |
| `description` | User/developer-visible capability provided by the primitive. |
| `owner` | Component that owns canonical state or validates declarations (`server`, `client`, or `server->client`). |
| `authority` | Boundary that may create, mutate, publish, or execute the primitive. |
| `hot_path_policy` | Manifest routing policy, async priority, or explicit `no-hot-path` rationale. |
| `js_module` | Proposed Clay JS facade module. |
| `js_export` | Proposed callable/export name, following Clay JS API naming rules. |
| `stable_id` | Proposed stable registry ID. Package-owned IDs must use the package prefix instead of `clay.*`. |
| `user_facing_name` | Search/help label for docs, command palette, and AI-agent lookup. |
| `permissions` | Required permission scope or `none` for inert declarations. |
| `budget_ref` | Budget constant from `src/perf/budgets.rs`, or `no-hot-path` with rationale. |
| `primitive_kind` | One of `manifest-data`, `server-first-command`, `SDUI-state`, `SDUI/component-state`, `layout-state`, `renderer/decorator-data`, `configuration-data`, or `package-ui/state-data`. |
| `documentation_metadata` | Required docs/registry metadata for later implementation phases. |
| `test_expectations` | Minimum coverage gate expected when implemented. |
| `status` | `Exists`, `Extend`, `New`, or `Deferred`. |

All entries inherit the Phase 16 security baseline documented in `docs/reference/primitives/package-security.md`: primitive declarations are schema-validated server-side, package provenance is retained through package identity and prefix metadata, raw `Deno.core.ops` calls are not part of public package APIs, and packages never execute JavaScript in Rust client keypress, paint, layout, or text-event handlers.

## Primitive Category Notes

### DocumentClassification

Document classification is intentionally server-owned. Packages declare static patterns; Clay chooses the active mode from validated metadata rather than allowing arbitrary file-system scans or client-side predicates. Classification may inspect open document metadata and bounded leading content if a future decision allows it, but the Phase 16 baseline only requires extension, filename, MIME hint, and declared package metadata.

Phase 18.9 extends classification with shebang and bounded leading-content probes plus a documented precedence ladder: user override > package-declared pattern (exact filename > wildcard > extension > MIME) > shebang line > bounded leading-content probe > `core.code` > `core.text`. Probes read only a bounded constant prefix of an already-open document supplied by the open path; they perform no filesystem scan, directory walk, or arbitrary package predicate, and oversize slices are rejected and classified to a fallback mode. Probe rules are declarative metadata validated like other patterns, with no language-specific Rust branches. The package-author contract for extending the built-in fallbacks is documented in [Creating Clay Packages — Phase 18.9 authoring contract](../packages/creating-packages.md#phase-189-authoring-contract-generic-textcode-fallback-modes-and-generic-key-behavior). See `docs/wiki/modules/phase18.9-generic-text-code-modes-primitive-review.md`.

### MajorModeActivation

A document has at most one active major mode. Activation publishes a new behavior version and the validated primitive set for that mode. The Rust client receives only inert behavior manifests, decoration updates, SDUI trees, and configuration state; it does not execute mode package JavaScript.

Phase 18.9 registers always-on built-in Clay-owned fallback modes `core.text` and `core.code` through this same primitive at server startup, with a documented built-in provenance marker and lowest precedence, so any document remains editable even when no language package is installed, disabled, or invalid. The `core.` mode-ID prefix is reserved for Clay-owned built-ins and cannot be registered by a package. Built-in modes require no `~/.config/clay/init.js` line or package load step; they are `MajorModeActivation`/`DocumentClassification` data registered by Clay itself, not new primitives.

### MinorModeActivation

Minor modes are overlays that must declare compatible major modes. They cannot silently replace a major mode's behavior, key binding, command, or decoration priority. Phase 16 records the primitive but defers implementation until a concrete minor-mode POC justifies the conflict surface.

### KeyRoutingOverride

Key routing reuses the existing behavior manifest and keybinding API where possible. Package-owned keybindings must preserve provenance and deterministic conflict handling. Client-first routes may only target known deterministic client edit authorities.

Phase 18.9 records fallback command routing for `core.text`/`core.code` keybindings that do not match a package-declared binding: unmatched keybindings fall back to the built-in `core.*` manifest rules rather than blocking input, and mode-specific fallback commands route through the Phase 18.8 `CommandExecution` path. No new primitive is introduced; routing remains inert manifest data validated by the existing `KeyRoutingOverride` surface.

### TextTransform

Text transforms cover auto-indent, pair insertion, continuation rules, and Markdown-style list/code-block continuation. They remain manifest data: packages may declare rule parameters, but the client executes only Rust-known transform kinds. The existing `EditorBehaviorRules` already provides generic `Enter` (`EnterRule::PreserveLeadingWhitespace`/`InsertNewlineOnly`/`ContinueLineMarkers`/`PreserveFenceBodyIndent`), `Tab` (`TabRule`), pair insertion (`PairRule`), comment continuation (`CommentContinuationRule`), and autocomplete triggers (`AutocompleteTrigger`) as `ClientFirstPredictable` manifest data executed by Rust-known engines with no client-side JavaScript and no IPC before local paint.

Phase 18.9 reuses these existing kinds for `core.text`/`core.code` fallback behavior and implements the electric-character manifest kind (`ElectricCharacterRule` + `ElectricEffect::OutdentOneLevel`) as an extension of the `EnterRule`/`PairRule` family for effects those rules cannot already express (e.g., auto-outdent reflow triggered by typing a closing bracket). Electric-character rules are declarative parameters a future language package can reuse; packages declare them under `clay.modes` editor rules via the `electricCharacters` field and only the `outdent-one-level` effect is accepted, unknown effects are dropped. They are not a new primitive category and introduce no client-side JavaScript, raw ops, native handles, raw CSS, or callbacks. `core.code` ships a default electric set for `}`/`)`/`]`; `core.text` ships none. Two default rule sets ship: `EditorBehaviorRules::default_text()` (plain text, no electric) via `BehaviorManifest::minimal_text_editing`, and `EditorBehaviorRules::default_code()` (code-oriented, with electric reflow) via `BehaviorManifest::core_code_editing`; `ModeRegistry::select_behavior_manifest_for_document` selects the `core.code` base manifest for the built-in `core.code` mode.

### IncrementalParseUpdate

Package parsers run server-side in the constrained JavaScript runtime as cancellable background work. Results carry document versions and are discarded if stale. Large-file handlers receive only validated `ParseWindowSnapshot` text slices selected from viewport/invalidated ranges, bounded by `ParsePolicy` and `SYNTAX_CACHE_BUDGET_BYTES`. For consecutive versions, `ParseInputEdit` preserves exact old/new byte and point coordinates against a stable window; incompatible cache state falls back to one bounded full parse. A native handler performs one parse/capture pass per accepted version/window and returns `IncrementalParseUpdate::decoration_updates`, whose independently bounded members are validated atomically. The client keeps the last validated decoration/fold state and interpolates inert decoration spans when parsing lags behind edits.

### DecorationRange

Decoration ranges are renderer/decorator data: byte spans, kind, style token, priority, provenance, document version, and viewport range. One parse/capture result may fan out into stable 128-byte `DecorationSet` chunks, ordered with changed/visible output first; chunk count is transport/cache work, not parser work. Empty syntax sets are authoritative range replacements and set-level package/layer identity keeps syntax replacement from erasing semantic data. The client may transform validated inert spans provisionally through optimistic edits, but only a current authoritative set becomes final. Ranges cannot contain draw callbacks, arbitrary styles that mutate native widgets, or executable code. `DecorationKind::Diagnostic` remains a visual tint layer only; message/code/source diagnostics use `DiagnosticSpan`.

### DiagnosticSpan

[`diagnostics.md`](diagnostics.md) is the authoritative range-diagnostic contract. `DiagnosticSet` carries document/version/viewport plus source-keyed replacement. Explicit package analyzers and future LSP bridges publish the same inert records; Tree-sitter recovery nodes remain decoration-only parser details and publish no diagnostics. Validation enforces `DIAGNOSTIC_PAYLOAD_BUDGET_BYTES` and related field/count limits; paint resolves severity colors through `StyleRegistry` and draws Clay-owned squiggles from cached Parley geometry. Diagnostics cannot select font roles or replace syntax/semantic decoration state.

### SemanticTypographyRole

[`typography.md`](typography.md) is the authoritative package/mode contract. Modes declare `defaultFontRole` (`monospace` or `proportional`), eligible syntax/semantic ranges declare optional `fontRole`, and text-bearing components declare optional `style.fontRole` (`ui`, `monospace`, or `proportional`). Omission inherits the enclosing default. User configuration alone owns concrete family fallback stacks and logical-pixel sizes through `theme.setTypography`.

The role is a field on existing primitives, not a new package setter or permission. Server validators reject concrete font fields and invalid role/layer/component combinations. Client layout resolves cached profiles and revisions with no package JavaScript, IPC, font file/URL access, or language-specific rendering branch in hot paths.

### SyntaxGrammarContribution

`SyntaxGrammarContribution` began in Phase 18.10 as package-provided Tree-sitter grammar metadata and is implemented in Phase 18.16 as one tiered syntax engine. Package metadata describes package-root-confined Tier 2 assets (`tree-sitter-wasm`, `highlights.scm`, optional locals/injections queries), capture-to-style-token mapping, language/file patterns, provenance, and parse/highlight budgets. Host-owned Tier 1 native descriptors add compiled first-party grammar data for Rust, TypeScript/TSX, JavaScript, and Markdown; Tier 3 retains package-JS parse handlers for grammar-less or explicitly JavaScript-selected packages.

All tiers remain separate from `MajorModeActivation`: a document can remain editable as `core.code` or `core.text` while selecting an active syntax grammar. Selection is data-driven by language/file patterns and `SyntaxEngineTier`, with no language-specific Rust branches. `setSyntaxEnginePreference(target, tier)` is the documented user-initiated override (`native`, `wasm`, or `javascript`/`js`); package load order cannot silently replace Tier 1.

For an accepted consecutive edit, the server carries one exact `ParseInputEdit` into the stable window. A matching cached tree receives `Tree::edit`, then one bounded parse/capture pass runs. Query ranges are the UTF-8-safe visible intersection of Tree-sitter changed ranges plus explicit invalidations; `QueryCursor::set_byte_range` returns intersecting complete captures, so package grammar boundaries—not whitespace, idle, or caret movement—define token/comment/string/prose/code corrections. One capture result fans out into complete stable 128-byte `DecorationSet` output ranges, with changed/visible chunks first and atomic per-member validation. Full/open/viewport work has no accepted edit and explicitly queries the bounded visible window.

Grammar validation and engine selection happen at package load, document open/reload, or explicit reclassification, not in keypress, paint, layout, scroll, pointer, or text-event handlers. Open returns before background parse completion; handler failures publish sanitized `RuntimeDiagnostic` values such as `parse.open_failed` rather than blocking or leaking paths/source text. The client may provisionally interpolate validated spans through optimistic edits; current server chunks replace affected package/layer ranges.

Phase 18.16 keeps first-party-only artifact loading, package-root confinement, no runtime downloads, no shell/package-manager/native-library loading, and no client-side JavaScript. Arbitrary third-party/native grammar trust remains out of scope until Phase 23 and a separate security decision. See `docs/wiki/modules/phase18.16-tiered-tree-sitter-engine-primitive-review.md` and `docs/reference/packages/creating-packages.md#phase-1816-authoring-contract-tiered-syntax-engine`.

### FoldingRange

Folding ranges are validated ranges plus labels/kinds. Collapsed state is client-local UI state, but range authority comes from server-validated package output.

### CompletionTriggerAndResult

Phase 18.11 promotes `CompletionTriggerAndResult` from deferred to implemented generic infrastructure. Trigger characters and word-boundary rules remain inert manifest data (`AutocompleteTrigger` with `RoutingPolicy::UiReactivePriority`); typing a trigger character edits locally first (`ClientFirstPredictable`) and then enqueues a typed `CompletionRequest` through a bounded non-blocking channel. Result computation runs server-side on a cancellable `UiReactivePriority` lane that aborts or stale-drops older in-flight requests and validates results against the current document/behavior version before publication. Display and acceptance reuse the Phase 18.8 `TransientMenuSession` bottom overlay path; a completion-specific adapter commits a validated text replacement instead of executing a command. The first implementation ships one built-in buffer-word provider; package providers require `completion-provider` permission and resolver-validated package provenance through `completion.serverRegisterCompletionProvider`.

Any future provider that needs workspace, network, AI, or shell authority must introduce explicit permissions and an approved decision log before implementation. See `docs/wiki/modules/phase18.11-completion-provider-primitive-review.md`.

Phase 18.19 adds three generic extensions on this primitive. Tasks 4-5 implement snippet text format, bounded client-local expansion, and `SnippetSession` navigation through the existing optimistic Replace/caret/selection paths. Task 6 implements opt-in `CompletionProviderMeta.exclusive` plus one shared `apply_exclusive_suppression` filter used by `ClayOpState` and coordinator trigger selection: an exclusive provider in the highest-priority tier retains equal-priority peers and suppresses only lower priorities; omitted descriptor fields default to `false`. Task 7 implements `completion.serverDisableCompletion`, a bounded config-time facade/op backed by a disabled-target `BTreeSet` and generation counter. Exact provider IDs and package names/API prefixes are filtered from both runtime snapshots and trigger selection; the coordinator rejects disabled scheduling and aborts older-generation work. Disable is idempotent, adds no permission or authority, and reload remains the minimal re-enable path. Task 8 adds generic structured item normalization (`string | { label, insertText, detail?, textFormat? }`), rejects mixed plain/snippet providers, merges matching static providers within existing result budgets, and ships dedicated priority-0 `rust.snippets` and `typescript.snippets` data through unchanged package permissions/load paths. See `docs/wiki/modules/phase18.19-completion-extensions-primitive-review.md`.

### LanguageIntelligenceRequestAndResult

Phase 18.20 adds one feature-tagged request/result family for hover, go-to-definition, code actions, and signature help. Canonical positions are UTF-8 byte offsets against an open document or a known workspace root plus normalized relative path. Results carry request ID, document/behavior/provider generations, package provenance, and typed `Ok`/`Empty`/`Timeout`/`ProviderError` statuses. Semantic tokens, diagnostics, and completion map onto existing `DecorationSet`, `DiagnosticSet`, and `CompletionResultSet` primitives rather than parallel transports. LSP wire types, JSON-RPC, and position-encoding conversion remain package-side; see [Language Intelligence and LSP 3.17 Bridge Contract](language-intelligence.md).

### LanguageServerSession

Phase 18.20 adds one host-owned opaque session conduit under deny-by-default `language-server` authority. Users call `authorizeLanguageServer` from `~/.config/clay/init.js` before `loadPackage`; first load seals grants. Sessions spawn only fixed validated contribution descriptors with approved-root cwd, `env_clear` plus declared inherits, piped stdio, hard message/session/stderr/timeout caps, sanitized diagnostics, and cleanup on withdrawal/reload/shutdown. This is trusted same-user subprocess authority, not an OS sandbox. LSP `Content-Length` framing and server initialization are Phase 18.21 adapter work layered on `send`/`read`/`stop`.

### CommandDeclaration

Commands are public programmatic surfaces and must have documentation metadata. Registration does not grant execution authority; command handlers must separately declare the permissions needed for document, workspace, AI, package, or other side effects. Phase 16 also plans a metadata-only command discovery API, `commands.serverListCommands`, which traces to this same `CommandDeclaration` category and grants no execution authority. Phase 18.9 adds two read-only built-in discovery commands registered through the same `CommandDeclaration` surface and surfaced in the Control Center: `modes.listActiveModes` and `modes.explainActiveMode`. They carry no permissions and read installed `ModeRegistry` state only (active mode, package vs `core` built-in provenance, classification source, fallback rationale); they never trigger filesystem scans, package evaluation, or any execution/document/workspace authority.

### CommandExecution

Command execution is the Phase 18.8 extension point for activating already registered commands. It must reuse `CommandRegistry` metadata and validate command ID, routing policy, package provenance, permissions, target context, bounded arguments, and action/session freshness before side effects. SDUI buttons, package UI action intents, behavior-manifest keybindings, and transient-menu selections should all normalize to this one server-owned boundary. Command execution is explicit server-first work, not ordinary edit, paint, layout, pointer, scroll, keypress, or text-event work; package JavaScript may run only behind the server execution path, never in the Rust client hot path.

Phase 24.2 completes the boundary for menu activation: a Control Center selection produces a typed `ServerMenuActivation` — a `CommandExecutionRequest` for server/package commands (dispatched with the live aggregated registry snapshot so package commands execute from the menu) or the narrow `ShellClientCommand` ID for `ClientUiCommand`-routed pane/tab commands, which ships as the bounded `ServerMessage::ShellClientCommandRequest { command_id }` frame and runs in the client shell driver (deny-by-default reparse; unknown/forged IDs dropped). One shared connection-level dispatcher (`execute_command_intent`) covers SDUI actions, command intents, and menu activation; only the menu path carries the live registry.

### SduiPanelStatusContribution

SDUI is the approved package UI contribution path for panels and status areas. It remains inert server-validated UI state. Public live SDUI state querying remains undecided and should not be inferred from internal Phase 15 observability types.

### Phase 22 Window-Model Rows (22.3–22.6)

`TabRegistryBinding` and `TabBarChrome` are Phase 22 window-model primitives. Phase 22.3 added the server-authoritative in-memory tab registry (one `ClientId` per tab; the registry binds already-authorized connections and grants nothing — workspace file grants stay per-connection and therefore per-tab, with disconnect/reclaim teardown releasing them; see the authority review recorded in plan 077 task 6 and `docs/wiki/modules/tabs-and-clients.md`) and the shell-owned tab bar rendered from registry snapshots. ### Phase 22.6 Accessibility Contract

Phase 22.6 adds the window-model accessibility contract, documented in `docs/development/accessibility.md`: the shell exposes a `TabList` with one `Tab` per card (sanitized workspace basename, `selected` on the active card) when two or more cards exist, numbered `Pane N of M` labels with sanitized document display names, and a single polite `Status` live-region node announcing tab activate/create/close and split add/remove/move exactly once per user action. Labels are sanitized (basename only, no host paths, 64-char name cap) and announcement strings share the 256-char transient-menu budget; both constants live in `src/perf/budgets.rs`. Inactive tabs' panes are unreachable from the accessibility root. The tab bar remains painted chrome with informational a11y nodes (no per-card widget focus; keyboard tab switching stays on the Phase 22.4 tab commands).

`PanelContribution`, `ComponentContribution`, and `TransientOverlayContribution` are SDUI/component-state primitives. Phase 18.3 implements them as runtime-backed `clay:ui` public APIs that extend the existing inert SDUI approach into slot-aware fixed panels, component catalog declarations, and transient overlay declarations. They preserve package provenance, action target validation, bounded payloads, structural observations, and deterministic conflict diagnostics while keeping Masonry/native details internal.

`TransientMenuSession` is a Phase 18.8 generic active-session primitive layered on the transient overlay/component family. It adds query text, selected index, bounded item records, status text, focus/dismissal state, session freshness, and selection activation semantics for command palettes and future pickers. It is not a Control Center-specific widget; Control Center is expected to consume this generic session model and activate selected items through `CommandExecution`.

Phase 24.1 implemented the session as server-owned per-connection state (`ServerMenuSessions`) with a bounded protocol round trip (`TransientMenuSnapshot`/`MenuQueryUpdate`/`MenuSelectionMove`/`MenuActivate`/`MenuCancel`/`TransientMenuClosed`) and clamped `TRANSIENT_MENU_*` budgets. Phase 24.2 stamped sessions with the runtime generation id (a replaced generation cancels the session and rejects stale activation), feeds them from the generation-safe live command catalogue (`RuntimeGenerationStore::command_catalogue_snapshot`: built-ins, declared `shell.client*` entries, trusted and third-party registry snapshots, deterministic sort, duplicate-ID fail-closed), and added the shared bounded fuzzy subsequence matcher for local query scoring. Phase 24.3 adds a second consumer, the Path Browser: `controlCenter.openPath` opens a `PathBrowserSession` (seeded from the active document's canonical parent, then the bound tab workspace root, then the server cwd) that lists a bounded depth-1 snapshot through `BuiltInUserBrowseListing` and navigates by primary activation (descend directory), secondary activation (open directory as the tab workspace), Backspace (ascend on an empty filter), or direct path-bar edits. Browse authority is ephemeral and user-authorized by the built-in surface itself: navigation alone creates no grant, a file open converts it into exactly one `SingleFile` grant, and an Alt+Enter workspace open converts it into exactly one `Directory` root grant; the native dialogs remain the fallback capability issuers. The session remains Clay-owned: `ui.serverOpenTransientMenu` was rejected (YAGNI) — packages cannot open, drive, or intercept menu sessions (including the Path Browser), receive paths from them, or emit the `ShellClientCommand` frame, and activation routes through `CommandExecution` or the `ShellClientCommand` bridge only.

`PackageThemeTokenDeclaration`, `PackageUiStateScope`, and `PackageLayoutOverride` cover package UI/state/configuration categories for Phases 18.3 and 18.4. Phase 18.3 implements typed package theme token declarations and typed component style-variable resolution. Phase 18.4 implements UI state-scope declarations, layout overrides, input declarations, and package-owned options as runtime-backed documented APIs. These rows require explicit package/user state scopes and documented `~/.config/clay/init.js`/Clay JS API override paths rather than hidden package metadata keys. The Phase 18.3 and Phase 18.4 contribution/configuration APIs are runtime-backed and registry-public through full `docs/reference/clay-js-api/` pages and generated registry entries.

All Phase 18.1 shell/layout rows are generic and reusable across packages and modes. ### PackageOwnedConfiguration

Configuration remains Clay JS API based. Concrete user-facing settings must be represented as documented APIs with `custom_properties`, not ad hoc settings hidden in package metadata. Phase 18.4 promotes `configuration.setPackageOption` for package-owned layout/input/action/theme/fallback options; `configuration.setModePreference`, `configuration.setDecorationTheme`, and `configuration.setParsePolicy` remain planned stubs for mode activation defaults, decoration style preferences, and parse timeout/unit/viewport-priority preferences. Package enable/disable is intentionally not exposed as a configuration API because `docs/reference/primitives/package-security.md` requires a future decision log and explicit permission model before that authority can exist.

### PackagePermissionDeclaration

Permission declarations are load-time package metadata. They cannot request filesystem outside open documents, network, shell, AI mutation, remote listeners, WASM execution, raw Deno ops, native widget mutation, or client-side JavaScript by default.

### Plan 061 Trust-Domain and Extension Rows

Plan 061 adds six generic primitives for the approved two-runtime trust model (`decision-logs/2026-07-21-0001-two-package-runtime-trust-domains.md`). They reuse existing `PackageService` records, authorization/grant matching, graph cycle detection and rollback, conflict policy, module allowlists, runtime/provider generations, provider registries, runtime snapshots, and package UI validation; only the domain/provenance/extension/adoption/replacement/cross-domain gaps are new. Their closed versioned schemas (`clay-extension-point-v1`, `clay-package-relation-v1`, `clay-package-approval-v1`, `clay-package-replacement-v1`, `clay-cross-domain-envelope-v1`) are locked in [Package Primitive Security and Provenance Requirements](package-security.md#package-runtime-trust-domains-and-extension-authority).

Rejected shapes for these rows: per-package Rust APIs or per-language branches (every first-party need maps to generic registries first), a generic actor/plugin framework, JavaScript-visible bearer identities or authority handles, and cross-runtime V8 object/function/promise sharing. Schemas are bounded inert metadata evaluated at install/adopt/load/reload time; no package graph or cross-domain JavaScript work enters typing, paint, layout, scroll, pointer, or local edit paths.

## Security Requirements Shared by All Categories

- Package-owned stable IDs and exports must carry the package prefix; only first-party Clay APIs may use `clay.*` stable IDs.
- Server validation must reject malformed schemas, unknown primitive kinds, oversize payloads, undeclared permissions, raw operation references, raw CSS/style strings, native widget handles, direct Masonry widget constructors, renderer callbacks, and client-side JavaScript hooks.
- Inert declarations with `permissions = none` still do not grant filesystem, network, shell, AI, WASM, native widget mutation, or raw-op authority.
- Permission-bearing primitives must be declared in package metadata and validated before load/enable succeeds.
- Runtime parse, completion, and command work executes server-side and asynchronously; the client receives validated data or server-routed intents only.
- Shell/layout primitives must reject raw `Deno.core.ops`, native widget handles, direct Masonry mutation, raw CSS, client-side JavaScript, Vello/Parley callbacks, duplicate slot/component/action IDs, unregistered action targets, unknown theme tokens, unsupported state scopes, hidden layout configuration keys, and oversize layout/component/state payloads with deterministic diagnostics.
